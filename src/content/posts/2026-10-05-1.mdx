Windowsの設定の多くは、レジストリの値で決まります。
グループポリシーの「管理用テンプレート」に並ぶ設定項目は、「どの設定を、どのレジストリキーのどの値に書き込むか」を定義したADMXというXMLファイルから作られています。

今回は、ADMXの役割と仕様、設定した値がどこに保存されてどのレジストリに書き込まれるのか、既存のADMXの読み方、Windowsデバイスで設定が評価されるしくみについて紹介します。

## ADMXとは

ADMXは、レジストリで制御できる設定の設計図です。
1つの設定項目について、次の2つを定義します。

- 「有効」「無効」や入力した値を、どのレジストリキーのどの値にどの型で書き込むか
- グループポリシーの管理エディタやローカルグループポリシーエディタ（`gpedit.msc`）に、どの分類でどのような入力欄を表示するか

ここで大切なのは、**ADMX自体は設定値を持たない**という点です。
管理者がエディタで選んだ状態や入力した値は、ADMXの定義に従って`Registry.pol`というファイルに保存されます。
Windowsデバイスはこのファイルを読んでレジストリに値を書き込み、OSやアプリケーションはそのレジストリの値を読んで動作を変えます。
値がどのパスに保存され、どのレジストリに書き込まれるのかは、「ADMX/ADMLファイルの仕様」で具体的に説明します。

```d2 title="ADMXの定義をもとにエディタで設定した値が、Registry.polを経由してWindowsデバイスのレジストリに書き込まれるまでの流れ"
grid-columns: 3
grid-gap: 40
admin: 管理者の操作 {
  admx: ADMX（定義） {shape: image; icon: /d2-icons/file-code.svg}
  adml: ADML（表示） {shape: image; icon: /d2-icons/languages.svg}
  editor: エディタ {shape: image; icon: /d2-icons/monitor-cog.svg}
  admx -> editor
  adml -> editor
}
gpo: GPO {
  pol: Registry.pol {shape: image; icon: /d2-icons/file-cog.svg}
}
client: Windowsデバイス {
  reg: レジストリ {shape: image; icon: /d2-icons/database.svg}
  app: OSやアプリ {shape: image; icon: /d2-icons/app-window.svg}
  app -> reg: 読み取る
}
admin.editor -> gpo.pol: 保存
gpo.pol -> client.reg: 書き込む
```

### ADMX、ADML、関連ファイルの違い

管理用テンプレートに関係するファイルは、いくつかあります。
名前が似ているので、役割の違いを整理します。

| ファイル | 役割 | 形式 | 置き場所 |
| --- | --- | --- | --- |
| ADMX（`.admx`） | ポリシーの定義（書き込むレジストリと値、エディタでの分類） | XML | `PolicyDefinitions`フォルダー |
| ADML（`.adml`） | 表示用の文字列と、入力欄などの画面部品の配置 | XML | `PolicyDefinitions`の下の言語別フォルダー（`ja-JP`など） |
| ADM（`.adm`） | 旧形式の管理用テンプレート。定義と表示用の文字列を1つのファイルに持つ | 独自のテキスト形式 | GPOごとのフォルダー |
| `Registry.pol` | エディタで設定した値そのもの | バイナリ | GPOごとのフォルダー（コンピュータ用とユーザー用） |

ADMXは言語に依存しない定義で、エディタに表示する文字列は`$(string.ID)`のような参照で書かれています。
この参照先の文字列を持つのが、言語ごとに用意されるADMLです。
同じADMXに日本語と英語のADMLを用意すれば、管理者は自分の言語で同じポリシーを設定できます。

ADMLが必要なのは、エディタのように人がポリシーを見て選ぶ場面だけです。
レジストリに書き込む値を決めるのに必要な情報は、すべてADMXにあります。

| 場面 | ADMX | ADML |
| --- | --- | --- |
| エディタでポリシーを表示、編集する | 必要 | 必要 |
| グループポリシーを適用するWindowsデバイス | 不要 | 不要 |
| MDMでADMXをWindowsデバイスに取り込む | 必要 | 不要 |

ADMは、Windows Vistaより前に使われていた形式です。
ADMはGPOを作るたびにGPOのフォルダーへコピーされていたため、同じファイルが大量に保存されていました。
ADMXではこのしくみがなくなり、GPOには設定値の`Registry.pol`だけが保存されるようになりました。
なお、Windows 10以降にはADM形式の管理用テンプレートは含まれていません。

## ADMX/ADMLファイルの仕様

ここからは、ADMXとADMLのXMLの書き方と、設定した値が保存される場所、書き込まれる場所を見ていきます。
要素の一覧は、Microsoft Learnの[PolicyDefinitions schema](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/policy/schema-root)にまとまっています。

### ADMXの構造

ADMXは、次のような構造になっています。

```xml title="ADMXの基本構造"
<?xml version="1.0" encoding="utf-8"?>
<policyDefinitions revision="1.0" schemaVersion="1.0"
  xmlns="http://schemas.microsoft.com/GroupPolicy/2006/07/PolicyDefinitions">
  <!-- このファイルの名前空間と、参照する他のファイルの名前空間 -->
  <policyNamespaces>
    <target prefix="smartscreen" namespace="Microsoft.Policies.SmartScreen" />
    <using prefix="windows" namespace="Microsoft.Policies.Windows" />
  </policyNamespaces>
  <!-- 対応するADMLの最小のリビジョン -->
  <resources minRequiredRevision="1.0" />
  <!-- 対応する製品やバージョンの定義（必要な場合だけ） -->
  <supportedOn>...</supportedOn>
  <!-- エディタでの分類 -->
  <categories>...</categories>
  <!-- ポリシーの定義 -->
  <policies>
    <policy>...</policy>
  </policies>
</policyDefinitions>
```

それぞれの要素の役割は次のとおりです。

| 要素 | 役割 |
| --- | --- |
| `policyDefinitions` | ルート要素。`revision`はこのファイルのリビジョン、`schemaVersion`はスキーマのバージョン |
| `policyNamespaces` | このファイルの名前空間（`target`）と、参照するほかのファイルの名前空間（`using`） |
| `resources` | 対応するADMLに求める最小のリビジョン（`minRequiredRevision`） |
| `supportedOn` | 「サポートされるバージョン」としてエディタに表示する定義 |
| `categories` | エディタのツリーに表示する分類（カテゴリ） |
| `policies` | ポリシーの定義の一覧 |

#### 名前空間とカテゴリ

`target`要素は、このADMXファイルの名前空間を宣言します。
名前空間はADMXファイルを識別するもので、ファイルごとに一意である必要があります。
同じ名前空間を持つADMXが2つあると、エディタはエラーを表示します。

`using`要素は、ほかのADMXファイルの定義を参照するときに使います。
`prefix`で付けた接頭辞を使って、`windows:WindowsComponents`のようにほかのファイルのカテゴリや`supportedOn`の定義を参照できます。

たとえば、Windows標準の`Windows.admx`はポリシーを1つも持たず、「Windows コンポーネント」などのカテゴリと、対応するWindowsのバージョンの定義だけを提供しています。
多くのADMXは、`Windows.admx`を参照して、自分のカテゴリを「Windows コンポーネント」の下に配置しています。

```d2 title="SmartScreen.admxがWindows.admxの名前空間、カテゴリ、対応バージョンの定義を参照する関係"
windows: Windows.admx {
  shape: sql_table
  target: 'Microsoft.Policies.Windows'
  category: 'WindowsComponents'
  supportedOn: 'SUPPORTED_Windows8'
}
smartscreen: SmartScreen.admx {
  shape: sql_table
  using: 'prefix="windows"'
  parentCategory: 'windows:WindowsComponents'
  supportedOn: 'windows:SUPPORTED_Windows8'
}
smartscreen.using -> windows.target
smartscreen.parentCategory -> windows.category
smartscreen.supportedOn -> windows.supportedOn
```

カテゴリは`category`要素で定義し、`parentCategory`要素で親のカテゴリを指定して階層を作ります。
親を指定しないカテゴリは、「管理用テンプレート」の直下に表示されます。

#### policy要素

`policy`要素が、エディタに表示される1つのポリシーです。
主な属性は次のとおりです。

| 属性 | 内容 |
| --- | --- |
| `name`（必須） | ポリシーの名前。ファイル内で一意にする |
| `class`（必須） | 適用対象。`Machine`、`User`、`Both`のいずれか |
| `displayName`（必須） | エディタに表示する名前。ADMLの文字列を`$(string.ID)`で参照する |
| `explainText`（任意） | ポリシーの説明。ADMLの文字列を参照する |
| `presentation`（任意） | 入力欄などの画面部品。ADMLの`presentation`を`$(presentation.ID)`で参照する |
| `key`（必須） | 書き込むレジストリキー。`HKEY_LOCAL_MACHINE`などのルートは含めない |
| `valueName`（任意） | 有効、無効を切り替えたときに書き込むレジストリの値の名前 |

子要素では、`parentCategory`で所属するカテゴリを、`supportedOn`で対応するバージョンを指定します。

#### 有効、無効のときに書き込む値

ポリシーの有効時と無効時に`valueName`へ書き込む値は、`enabledValue`と`disabledValue`で指定します。
値には、数値を表す`decimal`、文字列を表す`string`、値を削除する`delete`のいずれかを使います。

```xml title="有効で1、無効で0を書き込む例"
<policy name="ExamplePolicy" class="Machine" displayName="$(string.ExamplePolicy)"
  key="Software\Policies\ExampleApp" valueName="ExampleValue">
  <parentCategory ref="ExampleCategory" />
  <supportedOn ref="windows:SUPPORTED_Windows_10_0" />
  <enabledValue>
    <decimal value="1" />
  </enabledValue>
  <disabledValue>
    <decimal value="0" />
  </disabledValue>
</policy>
```

1つのポリシーで複数の値を書き込みたい場合は、`enabledList`と`disabledList`を使います。
`item`要素ごとに`key`と`valueName`を指定できるので、`policy`要素の`key`とは別のキーにも書き込めます。

```xml title="有効にしたときに2つのキーへ書き込み、無効にしたときに片方の値を削除する例"
<policy name="ExampleListPolicy" class="Machine" displayName="$(string.ExampleListPolicy)"
  key="Software\Policies\ExampleApp">
  <parentCategory ref="ExampleCategory" />
  <supportedOn ref="windows:SUPPORTED_Windows_10_0" />
  <enabledList>
    <item key="Software\Policies\ExampleApp" valueName="FeatureEnabled">
      <value>
        <decimal value="1" />
      </value>
    </item>
    <item key="Software\Policies\ExampleApp\Feature" valueName="Mode">
      <value>
        <string>Strict</string>
      </value>
    </item>
  </enabledList>
  <disabledList>
    <item key="Software\Policies\ExampleApp" valueName="FeatureEnabled">
      <value>
        <decimal value="0" />
      </value>
    </item>
    <item key="Software\Policies\ExampleApp\Feature" valueName="Mode">
      <value>
        <delete />
      </value>
    </item>
  </disabledList>
</policy>
```

`enabledValue`と`disabledValue`はどちらも任意ですが、Microsoftのリファレンスは、`enabledValue`を省略するとエディタが有効、無効、未構成の状態を正しく表示できない場合があると注意しています。
自作のADMXでは、両方を明示しておくのが無難だと思います。

#### elements要素

有効にしたポリシーで文字列や数値などの入力を受け付けたい場合は、入力項目を`elements`要素で定義します。
それぞれの項目は、`valueName`で指定したレジストリの値に書き込まれます。
`key`を省略すると、`policy`要素の`key`が使われます。

| 要素 | 内容 | 書き込まれる値 |
| --- | --- | --- |
| `boolean` | オンとオフの2択 | `trueValue`と`falseValue`で指定した値 |
| `decimal` | 数値 | `REG_DWORD`（`storeAsText="true"`の場合は文字列） |
| `longDecimal` | 64ビットの数値 | `REG_QWORD` |
| `text` | 1行の文字列 | `REG_SZ`（`expandable="true"`の場合は`REG_EXPAND_SZ`） |
| `multiText` | 複数行の文字列 | `REG_MULTI_SZ` |
| `enum` | 選択肢から1つを選ぶ | 選んだ`item`の`value`で指定した値 |
| `list` | 複数の項目の一覧 | 指定したキーの下に、項目ごとの値 |

`elements`の各項目には`id`を付けます。
この`id`は、ADMLの画面部品と対応付けるために使います。

`list`は、1つのキーの下に複数の値を書き込む項目です。
`valuePrefix`を指定すると、`valuePrefix`に連番を付けた名前の値が作られます。
`explicitValue="true"`にすると、管理者が値の名前とデータの両方を入力します。
デフォルトでは、ポリシーの適用時にそのキーの既存の値を削除してから一覧の値を書き込みますが、`additive="true"`にすると既存の値を残したまま追加します。

### ADMLの構造

ADMLは、ADMXに対応する言語ごとのファイルです。
次のような構造になっています。

```xml title="ADMLの基本構造"
<?xml version="1.0" encoding="utf-8"?>
<policyDefinitionResources revision="1.0" schemaVersion="1.0"
  xmlns="http://schemas.microsoft.com/GroupPolicy/2006/07/PolicyDefinitions">
  <displayName>表示名</displayName>
  <description>説明</description>
  <resources>
    <!-- displayNameやexplainTextから参照される文字列 -->
    <stringTable>
      <string id="ExamplePolicy">ポリシーの表示名</string>
    </stringTable>
    <!-- presentation属性から参照される画面部品の配置 -->
    <presentationTable>
      <presentation id="ExamplePolicy">
        <textBox refId="ExampleText">
          <label>入力欄の説明:</label>
        </textBox>
      </presentation>
    </presentationTable>
  </resources>
</policyDefinitionResources>
```

`stringTable`には、ADMXの`$(string.ID)`から参照される文字列を定義します。
`presentationTable`には、ADMXの`$(presentation.ID)`から参照される画面部品の並びを定義します。
画面部品は`refId`属性で、ADMXの`elements`の`id`と対応付けます。

| ADMLの画面部品 | 対応するADMXの要素 | エディタでの表示 |
| --- | --- | --- |
| `checkBox` | `boolean` | チェックボックス |
| `decimalTextBox` | `decimal` | 数値の入力欄 |
| `longDecimalTextBox` | `longDecimal` | 数値の入力欄 |
| `textBox` | `text` | 1行の入力欄 |
| `comboBox` | `text` | 候補を選べる入力欄 |
| `multiTextBox` | `multiText` | 複数行の入力欄 |
| `dropdownList` | `enum` | ドロップダウンリスト |
| `listBox` | `list` | 一覧を編集する画面を開くボタン |
| `text` | なし | 説明の文字列だけを表示 |

ADMXとADMLの参照関係をまとめると、次のようになります。

```d2 title="ADMXのpolicy要素の属性とelementsが、ADMLのstringTableとpresentationTableを参照する関係"
admx: ADMX {
  shape: sql_table
  displayName: '$(string.ID)'
  explainText: '$(string.ID_Help)'
  presentation: '$(presentation.ID)'
  elements: 'enum id="List"'
}
adml: ADML {
  shape: sql_table
  string: 'string id="ID"'
  help: 'string id="ID_Help"'
  presentation: 'presentation id="ID"'
  control: 'dropdownList refId="List"'
}
admx.displayName -> adml.string
admx.explainText -> adml.help
admx.presentation -> adml.presentation
admx.elements -> adml.control
```

### 値が書き込まれるレジストリの場所

`policy`要素の`class`属性によって、ポリシーが表示される場所と、値が書き込まれるレジストリのルートが決まります。

| `class` | エディタでの表示場所 | 書き込み先のルート |
| --- | --- | --- |
| `Machine` | コンピューターの構成 | `HKEY_LOCAL_MACHINE`（`HKLM`） |
| `User` | ユーザーの構成 | `HKEY_CURRENT_USER`（`HKCU`） |
| `Both` | 両方 | 設定した側に応じて、どちらか |

`key`属性にはルートを含めないので、実際に書き込まれる場所は「`class`で決まるルート + `key` + `valueName`」です。
たとえば、`class="Machine"`で`key="Software\Policies\Microsoft\Windows\System"`、`valueName="EnableSmartScreen"`と定義されているとします。
この場合は、`HKLM\Software\Policies\Microsoft\Windows\System`キーの`EnableSmartScreen`という値に書き込まれます。
同じ`key`でも、`class`によって書き込み先は変わります。

ADMXが書き込めるのは、`HKLM`と`HKCU`の配下だけです。
`HKEY_CLASSES_ROOT`など、ほかのルートの配下は指定できません。

### Software\Policies配下とそれ以外のキー

`key`には、`HKLM`と`HKCU`の配下であればどのキーでも指定できます。
ただし、Microsoftは次の4つのキーをポリシー用の場所と定めていて、Windows標準のADMXのほとんどはこの配下に書き込みます。

- `HKLM\Software\Policies`（推奨）
- `HKLM\Software\Microsoft\Windows\CurrentVersion\Policies`
- `HKCU\Software\Policies`（推奨）
- `HKCU\Software\Microsoft\Windows\CurrentVersion\Policies`

これらのキーに書き込まれる設定は、「管理されたポリシー（Managed）」として扱われます。
これらのキーは標準ユーザーには書き換えられないように保護されていて、GPOの適用対象から外れると、グループポリシーのクライアントは値を削除します。
また、ポリシーの値はアプリケーション自身が保存する通常の設定（Preference）とは別のキーにあるため、ポリシーを外せばもとの設定に戻ります。

一方で、`Software\Policies`以外のキーに書き込むADMXも作れます。
たとえば、アプリケーションが自分の設定を保存している`HKCU\Software\ExampleApp`に、ADMXから直接値を書き込むこともできます。
しかし、このようなキーに書き込んだ値は「管理されていないポリシー（Unmanaged）」として扱われ、GPOの適用対象から外れても値が残り続けます。
レジストリに設定が残り続ける状態は、「入れ墨（tattooing）」と呼ばれることもあります。

エディタは、デフォルトでは管理されていないポリシーも表示します。
フィルタオプションの「管理」で表示を絞ると、管理されたポリシーだけを表示できます。

自作のADMXでは、書き込み先を`Software\Policies`の配下にしておくのがよいと思います。
ポリシー用のキー以外に書き込む必要がある場合は、値を戻す手段を用意しておく必要があります。

参考：[Implementing Registry-Based Group Policy for Applications](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-2000-server/bb742499(v=technet.10))

### 設定した値が保存される場所

エディタでポリシーを設定しても、その場でレジストリに値が書き込まれるわけではありません。
エディタはADMXの定義をもとに、書き込むレジストリのキー、値の名前、型、データを`Registry.pol`に記録します。

`Registry.pol`はGPOごとに2つあり、コンピューターの構成は`Machine`フォルダー、ユーザーの構成は`User`フォルダーに保存されます。
GPOがどこにあるかで、`Registry.pol`のパスは次のように変わります。

- ローカルGPO（`gpedit.msc`で編集）
  - `C:\Windows\System32\GroupPolicy\Machine\Registry.pol`
  - `C:\Windows\System32\GroupPolicy\User\Registry.pol`
- ドメインのGPO
  - `\\<ドメイン名>\SYSVOL\<ドメイン名>\Policies\{GPOのGUID}\Machine\Registry.pol`
  - `\\<ドメイン名>\SYSVOL\<ドメイン名>\Policies\{GPOのGUID}\User\Registry.pol`

ローカルGPOは、ドメインに参加していないWindowsデバイスにもあります。
`gpedit.msc`で設定した値は、そのデバイスの`C:\Windows\System32\GroupPolicy`の下に保存されます。
ドメインのGPOでは、同じ構造のフォルダーがドメインの共有フォルダー（SYSVOL）にあり、適用対象のWindowsデバイスがそこから`Registry.pol`を読み取ります。
どちらの場合も、`Registry.pol`を読み取ってレジストリに書き込むのはWindowsデバイス自身です。

`Registry.pol`の中身は、`PReg`というシグネチャとバージョンのヘッダに続いて、次の形式のエントリが並んだものです。

```text title="Registry.polのエントリの形式"
[キー;値の名前;型;サイズ;データ]
```

キーには`HKLM`などのルートを含めず、ファイルの置き場所（`Machine`または`User`）でルートが決まります。
エントリは先頭から順に処理されるので、同じ値に対するエントリが複数あれば、後のエントリが優先されます。
値の名前には、次のような特別な指定もあります。

| 値の名前 | 意味 |
| --- | --- |
| `**del.値の名前` | その値を削除する |
| `**DeleteValues` | データにセミコロン区切りで指定した値を削除する |
| `**DelVals.` | そのキーの値をすべて削除する |
| `**DeleteKeys` | データにセミコロン区切りで指定したサブキーを削除する |

ADMXの`delete`要素や、`list`の既存の値の削除は、この削除の指定に対応しています。
詳しくは、Microsoft Learnの[Registry Policy File Format](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/policy/registry-policy-file-format)を参照してください。

このように、`Registry.pol`には「どのキーにどの値をどの型で書くか」がすでに具体的に記録されています。
そのため、`Registry.pol`を適用するWindowsデバイスには、ADMXとADMLのどちらも必要ありません。

## 簡単な例：ADMXを書いてみる

ここまでの仕様を使って、架空のアプリケーション「ExampleApp」のADMXを書いてみます。
次の3つのポリシーを定義します。

- 自動更新を無効にする（コンピューターの構成、有効と無効の切り替えだけ）
- 更新サーバーを指定する（コンピューターの構成、文字列と数値の入力）
- 起動時のヒント（ユーザーの構成、チェックボックス）

```xml title="ExampleApp.admx"
<?xml version="1.0" encoding="utf-8"?>
<policyDefinitions revision="1.0" schemaVersion="1.0"
  xmlns="http://schemas.microsoft.com/GroupPolicy/2006/07/PolicyDefinitions">
  <policyNamespaces>
    <target prefix="exampleapp" namespace="Example.Policies.ExampleApp" />
  </policyNamespaces>
  <resources minRequiredRevision="1.0" />
  <supportedOn>
    <definitions>
      <definition name="SUPPORTED_ExampleApp_1_0"
        displayName="$(string.SUPPORTED_ExampleApp_1_0)" />
    </definitions>
  </supportedOn>
  <categories>
    <category name="ExampleApp" displayName="$(string.ExampleApp)" />
    <category name="Update" displayName="$(string.Update)">
      <parentCategory ref="ExampleApp" />
    </category>
  </categories>
  <policies>
    <policy name="DisableAutoUpdate" class="Machine"
      displayName="$(string.DisableAutoUpdate)"
      explainText="$(string.DisableAutoUpdate_Help)"
      key="Software\Policies\ExampleApp" valueName="DisableAutoUpdate">
      <parentCategory ref="Update" />
      <supportedOn ref="SUPPORTED_ExampleApp_1_0" />
      <enabledValue>
        <decimal value="1" />
      </enabledValue>
      <disabledValue>
        <decimal value="0" />
      </disabledValue>
    </policy>
    <policy name="UpdateServer" class="Machine"
      displayName="$(string.UpdateServer)"
      explainText="$(string.UpdateServer_Help)"
      presentation="$(presentation.UpdateServer)"
      key="Software\Policies\ExampleApp">
      <parentCategory ref="Update" />
      <supportedOn ref="SUPPORTED_ExampleApp_1_0" />
      <elements>
        <text id="UpdateServerUrl" valueName="UpdateServerUrl" required="true" />
        <decimal id="CheckIntervalHours" valueName="CheckIntervalHours"
          minValue="1" maxValue="168" />
      </elements>
    </policy>
    <policy name="StartupTips" class="User"
      displayName="$(string.StartupTips)"
      explainText="$(string.StartupTips_Help)"
      presentation="$(presentation.StartupTips)"
      key="Software\Policies\ExampleApp">
      <parentCategory ref="ExampleApp" />
      <supportedOn ref="SUPPORTED_ExampleApp_1_0" />
      <elements>
        <boolean id="ShowTips" valueName="ShowTips">
          <trueValue>
            <decimal value="1" />
          </trueValue>
          <falseValue>
            <decimal value="0" />
          </falseValue>
        </boolean>
      </elements>
    </policy>
  </policies>
</policyDefinitions>
```

```xml title="ja-JP/ExampleApp.adml"
<?xml version="1.0" encoding="utf-8"?>
<policyDefinitionResources revision="1.0" schemaVersion="1.0"
  xmlns="http://schemas.microsoft.com/GroupPolicy/2006/07/PolicyDefinitions">
  <displayName>ExampleAppのポリシー</displayName>
  <description>ExampleAppを管理するためのポリシーです。</description>
  <resources>
    <stringTable>
      <string id="SUPPORTED_ExampleApp_1_0">ExampleApp 1.0以降</string>
      <string id="ExampleApp">ExampleApp</string>
      <string id="Update">更新</string>
      <string id="DisableAutoUpdate">自動更新を無効にする</string>
      <string id="DisableAutoUpdate_Help">有効にすると、ExampleAppは更新を自動で確認しません。</string>
      <string id="UpdateServer">更新サーバーを指定する</string>
      <string id="UpdateServer_Help">ExampleAppが更新を確認するサーバーと間隔を指定します。</string>
      <string id="StartupTips">起動時のヒント</string>
      <string id="StartupTips_Help">ExampleAppの起動時にヒントを表示するかどうかを指定します。</string>
    </stringTable>
    <presentationTable>
      <presentation id="UpdateServer">
        <textBox refId="UpdateServerUrl">
          <label>更新サーバーのURL:</label>
        </textBox>
        <decimalTextBox refId="CheckIntervalHours" defaultValue="24">確認する間隔（時間）:</decimalTextBox>
      </presentation>
      <presentation id="StartupTips">
        <checkBox refId="ShowTips" defaultChecked="true">起動時にヒントを表示する</checkBox>
      </presentation>
    </presentationTable>
  </resources>
</policyDefinitionResources>
```

`ExampleApp.admx`を`PolicyDefinitions`フォルダーに、`ExampleApp.adml`をその下の`ja-JP`フォルダーに置くと、エディタに次のように表示されます。

- コンピューターの構成 > 管理用テンプレート > ExampleApp > 更新
  - 自動更新を無効にする
  - 更新サーバーを指定する
- ユーザーの構成 > 管理用テンプレート > ExampleApp
  - 起動時のヒント

書き込み先のキーは、コンピューターの構成のポリシーが`HKLM\Software\Policies\ExampleApp`、ユーザーの構成のポリシーが`HKCU\Software\Policies\ExampleApp`です。
それぞれのポリシーを設定すると、次の値が書き込まれます。

| ポリシー | 設定 | 値の名前 | 値（型） |
| --- | --- | --- | --- |
| 自動更新を無効にする | 有効 | `DisableAutoUpdate` | `1`（`REG_DWORD`） |
| 自動更新を無効にする | 無効 | `DisableAutoUpdate` | `0`（`REG_DWORD`） |
| 更新サーバーを指定する | 有効 | `UpdateServerUrl` | 入力したURL（`REG_SZ`） |
| 更新サーバーを指定する | 有効 | `CheckIntervalHours` | 入力した数値（`REG_DWORD`） |
| 起動時のヒント | 有効 | `ShowTips` | チェックありは`1`、なしは`0`（`REG_DWORD`） |

「起動時のヒント」の`policy`要素には`valueName`がないので、値を書き込むのは`elements`の`boolean`だけです。
このように、ポリシー自体の有効、無効を値として書き込むかどうかも、ADMXの書き方で決まります。

たとえば、`gpedit.msc`で「自動更新を無効にする」を有効にすると、`C:\Windows\System32\GroupPolicy\Machine\Registry.pol`に次の内容のエントリが記録されます。
ここでは読みやすいように、型と数値をテキストで表しています。

```text title="Registry.polに記録されるエントリの内容"
[Software\Policies\ExampleApp;DisableAutoUpdate;REG_DWORD;4;1]
```

グループポリシーが適用されると、このエントリから`HKLM\Software\Policies\ExampleApp`キーの`DisableAutoUpdate`に`1`が書き込まれます。

## 既存のADMXの読み方

次に、Windows標準のADMXを読んでみます。
題材には、ファイルやアプリケーションの安全性を確認するMicrosoft Defender SmartScreenの`SmartScreen.admx`を使います。
抜粋は、Windows 11 2026 Update（26H2）向けの管理用テンプレートのものです。

Windows標準のADMXは、Windowsデバイスの`C:\Windows\PolicyDefinitions`にあります。
最新のものは、Microsoftのダウンロードセンターで配布されている管理用テンプレートからも入手できます。

<LinkCard href="https://www.microsoft.com/en-us/download/details.aspx?id=108847" />

ここでは、「Windows Defender SmartScreen を構成します」というポリシーを例に、書き込まれるレジストリの値を調べます。
このポリシーは、エディタの「コンピューターの構成 > 管理用テンプレート > Windows コンポーネント > Windows Defender SmartScreen > エクスプローラー」にあります。

```d2 title="エディタの表示名から、ADML、ADMXを順にたどってレジストリの値を調べる手順"
direction: down
name: "1. エディタの表示名\n「Windows Defender SmartScreen を構成します」"
id: "2. ADMLで文字列のIDを探す\nShellConfigureSmartScreen"
policy: "3. ADMXでIDを参照するpolicyを探す\ndisplayName属性の参照先"
reg: "4. class、key、valueName、elementsを読む\nEnableSmartScreen、ShellSmartScreenLevel"
name -> id -> policy -> reg
```

### ADMLで文字列のIDを探す

まず、日本語のADML（`ja-JP\SmartScreen.adml`）から、エディタに表示されている名前を探します。
該当する部分を抜粋します。

```xml title="ja-JP/SmartScreen.adml（抜粋）" {4,10-13}
<stringTable>
  <string id="SmartScreen">Windows Defender SmartScreen</string>
  <string id="Shell">エクスプローラー</string>
  <string id="ShellConfigureSmartScreen">Windows Defender SmartScreen を構成します</string>
  <string id="SmartScreen_PreventBypass">警告してバイパスを回避</string>
  <string id="SmartScreen_Warn">警告</string>
  <!-- 省略 -->
</stringTable>
<presentationTable>
  <presentation id="ShellConfigureSmartScreen">
    <dropdownList refId="ShellConfigureSmartScreen_Dropdown" noSort="true"
      defaultItem="0">次のいずれかの設定を選択してください。</dropdownList>
  </presentation>
</presentationTable>
```

表示名の文字列のIDは`ShellConfigureSmartScreen`です。
また、このポリシーには`ShellConfigureSmartScreen`という`presentation`があり、ドロップダウンリスト（`dropdownList`）が1つ配置されていることもわかります。

### ADMXでpolicyを探す

次に、ADMX（`SmartScreen.admx`）から、`$(string.ShellConfigureSmartScreen)`を参照している`policy`要素を探します。

```xml title="SmartScreen.admx（抜粋）" {18,25-38}

      <parentCategory ref="Shell" />
      <supportedOn ref="windows:SUPPORTED_Windows8" />
```

この抜粋から、次のことが読み取れます。

- 名前空間は`Microsoft.Policies.SmartScreen`で、`Windows.admx`（`windows`）と、Microsoft Edgeの旧版のADMX（`edge`）を参照している
- カテゴリは「Windows コンポーネント > Windows Defender SmartScreen > エクスプローラー」の階層になっている
- `class="Machine"`のため、「コンピューターの構成」に表示され、`HKLM`に書き込まれる
- 有効にすると`EnableSmartScreen`に`1`、無効にすると`0`が書き込まれる
- 有効にしたときは、ドロップダウンリストで選んだ項目に応じて、`ShellSmartScreenLevel`に`Block`か`Warn`の文字列が書き込まれる

### 書き込まれるレジストリの値

読み取った内容をまとめると、このポリシーを設定したときに書き込まれる値は次のようになります。
書き込み先のキーは`HKLM\Software\Policies\Microsoft\Windows\System`です。

- 有効にして「警告してバイパスを回避」を選んだ場合は、`EnableSmartScreen`に`1`、`ShellSmartScreenLevel`に`Block`
- 有効にして「警告」を選んだ場合は、`EnableSmartScreen`に`1`、`ShellSmartScreenLevel`に`Warn`
- 無効にした場合は、`EnableSmartScreen`に`0`

ADMLで表示名からIDを見つけ、ADMXでそのIDを参照する`policy`をたどれば、どのADMXでも同じ手順でレジストリの値を調べられます。
サードパーティー製アプリケーションのADMXでも、読み方は変わりません。

## ADMXファイルの配置と読み込み

ADMXとADMLは、エディタが読み込める場所に置く必要があります。
置き場所には、ローカルストアとセントラルストアの2つがあります。

ローカルストアは、各Windowsデバイスにあるデフォルトの置き場所です。
パスは`C:\Windows\PolicyDefinitions`で、`gpedit.msc`はここにあるADMXを読み込みます。
セントラルストアは、ドメインの管理者が同じADMXを共有するための置き場所です。
パスは`\\<ドメイン名>\SYSVOL\<ドメイン名>\Policies\PolicyDefinitions`で、グループポリシーのツールはセントラルストアがあればそちらのADMXを使います。

どちらの置き場所でも、ADMXはフォルダーの直下に、ADMLは言語別のフォルダー（`ja-JP`、`en-US`など）に置きます。

```d2 title="エディタがADMXとADMLを読み込む場所を決める流れ"
direction: down
central: セントラルストアがある {shape: diamond}
useCentral: セントラルストアのADMXを使う
useLocal: ローカルストアのADMXを使う
lang: 表示言語のADMLがある {shape: diamond}
useLang: 表示言語のADMLで表示
useFallback: 代替の言語のADMLで表示
central -> useCentral: はい
central -> useLocal: いいえ
useCentral -> lang
useLocal -> lang
lang -> useLang: はい
lang -> useFallback: いいえ
```

表示言語のADMLがない場合は、代替の言語のADMLが使われます。
ADMXの`resources`要素には、この代替の言語を指定する`fallbackCulture`属性があり、デフォルト値は`en-US`です。
日本語のADMLがないサードパーティー製アプリケーションのポリシーが英語で表示されるのは、このためです。

### 読み込み時のエラー

ADMXとADMLの組み合わせに問題があると、エディタを開いたときにエラーが表示されます。
よく見かけるのは、次の2つです。

- 同じ名前空間のADMXが複数ある：`Namespace '...' is already defined as the target namespace for another file in the store.`
- ADMXから参照される文字列がADMLにない：`Resource '$(string.ID)' referenced in attribute displayName could not be found.`

前者は、ファイル名を変えた新しいADMXを追加して、古いADMXが残っている場合などに起こります。
後者は、ADMXとADMLのバージョンが食い違っている場合などに起こります。

### ADMXを更新するときの注意点

新しいWindowsの管理用テンプレートをセントラルストアに反映するときは、既存のフォルダーへ上書きコピーしないほうが安全です。
Microsoftは、新しいバージョン用のフォルダー（`PolicyDefinitions-26H2`など）を作ってファイルをそろえてから、フォルダー名を入れ替える手順を紹介しています。
問題が起きた場合も、古いフォルダーに戻せます。

また、ダウンロードセンターで配布されている管理用テンプレートは、セントラルストアで使うためのものです。
`C:\Windows\PolicyDefinitions`のファイルを置き換える使い方はサポートされていないので注意してください。

<LinkCard href="https://learn.microsoft.com/en-us/troubleshoot/windows-client/group-policy/create-and-manage-central-store" />

## Windowsデバイスでどのように評価されるのか

最後に、`Registry.pol`に保存された値が、Windowsデバイスでどのように評価されてレジストリに書き込まれるのかを説明します。

Windowsデバイスでは、Group Policyサービス（`gpsvc`）が適用対象のGPOを決め、GPOごとの`Registry.pol`を読み取ります。
読み取った内容は、レジストリを担当するクライアント側の拡張機能（Registry CSE）に渡され、Registry CSEがレジストリに値を書き込みます。
ローカルGPOの`Registry.pol`はデバイス自身にあり、ドメインのGPOの`Registry.pol`はSYSVOLから読み取ります。

```d2 title="Group PolicyサービスがRegistry.polを読み取り、Registry CSEがレジストリに書き込むまでのシーケンス"
shape: sequence_diagram
pol: GPOのRegistry.pol
gpsvc: Group Policyサービス
cse: Registry CSE
reg: レジストリ
gpsvc -> pol: 読み取る
pol -> gpsvc: エントリの一覧
gpsvc -> cse: 適用を依頼
cse -> reg: 順に書き込む
```

### 適用のタイミング

グループポリシーは、次のタイミングで適用されます。

- コンピューターの構成は、Windowsの起動時
- ユーザーの構成は、ユーザーのサインイン時
- 起動中やサインイン中は、バックグラウンドで定期的に更新

バックグラウンドでの更新は、デフォルトで90分ごとに、0〜30分のランダムな時間を加えて行われます。
多くのWindowsデバイスが同時に問い合わせないように、ランダムな時間を加えています。
なお、ドメインコントローラ自身は5分ごとに更新されます。
これらのデフォルト値は、Windows標準のADMX（`GroupPolicy.admx`）にある「コンピューターのグループ ポリシーの更新間隔を設定する」などのポリシーの説明で確認できます。

すぐに適用したい場合は、Windowsデバイスで次のコマンドを実行します。

```powershell
gpupdate /force
```

### 適用の順序

1台のWindowsデバイスには、複数のGPOを適用できます。
GPOはローカル、サイト、ドメイン、OU（組織単位）の順に適用され、後から適用されたGPOの設定が優先されます。
それぞれの頭文字を取って、LSDOUと呼ばれることもあります。

ドメインに参加していないWindowsデバイスでは、ローカルGPOだけが適用されます。
`Registry.pol`の中でも、エントリは先頭から順に処理されるため、同じ値に対する指定が重なった場合は後のものが残ります。

### 未構成、有効、無効の違い

エディタのポリシーには、「未構成」「有効」「無効」の3つの状態があります。

| 状態 | `Registry.pol`に記録される内容 |
| --- | --- |
| 未構成 | 何も記録しない。このGPOではそのポリシーを管理しない |
| 有効 | ADMXの`enabledValue`、`enabledList`、`elements`で定義した値 |
| 無効 | ADMXの`disabledValue`や`disabledList`で定義した値 |

「無効」と「未構成」は、同じ意味ではありません。
「無効」は、無効を表す値（SmartScreenの例では`EnableSmartScreen`に`0`）を明示的に書き込みます。
一方で「未構成」は何も書き込まないので、ほかのGPOの設定や、OSやアプリケーションのデフォルトの動作がそのまま使われます。
有効や無効にしていたポリシーを未構成に戻すと、`Software\Policies`配下などの管理されたポリシーの値は、次の適用時に削除されます。

### 適用結果の確認方法

ポリシーが期待どおりに適用されているかは、Windowsデバイスで次の方法を使って確認できます。

- `gpresult /h report.html`で、適用されたGPOと設定をHTMLのレポートに出力する
- `gpresult /r`で、適用されたGPOの一覧をコマンドプロンプトに表示する
- `regedit`で、ADMXから読み取ったキーと値を直接確認する

既存のADMXの読み方を知っていれば、レポートの設定名から書き込まれるはずのレジストリを特定して、`regedit`で実際の値と照らし合わせられます。

### MDMでの評価との違い

ここまではグループポリシーの場合のしくみです。
Microsoft IntuneなどのMDMでADMXのポリシーを配布する場合は、`Registry.pol`とGroup Policyサービスのどちらも使われません。

MDMでは、Windowsデバイス自身がADMXの定義を持っていて、MDMから受け取った「有効」「無効」と入力値を、その定義に従ってレジストリに変換します。
Windows標準のADMXはOSに組み込まれていて、サードパーティー製アプリケーションのADMXは、ADMXのXMLをそのままMDMからWindowsデバイスに取り込みます。
このとき、ポリシーを指定するのに使うのは、エディタの表示名ではなく、ADMXの`policy`要素の`name`、カテゴリの`name`、`elements`の`id`です。
今回紹介した読み方は、そのまま役に立ちます。

IntuneでのADMXの使い方については、別の記事で紹介する予定です。
MDMでのしくみの詳細は、Microsoft Learnの[Understanding ADMX policies](https://learn.microsoft.com/en-us/windows/client-management/understanding-admx-backed-policies)を参照してください。

## 終わりに

今回は、ADMXの役割と仕様、設定した値が保存される`Registry.pol`と書き込まれるレジストリの場所、既存のADMXの読み方、Windowsデバイスで設定が評価されるしくみについて紹介しました。
