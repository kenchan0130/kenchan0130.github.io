前回の[ADMXのしくみと読み方](/post/2026-10-05-1)では、ADMXがレジストリのどこに何を書き込むかを定義するファイルであることを紹介しました。
ADMXは、もともとActive Directoryのグループポリシーで使われてきたしくみです。
現在は、ADMXの設定を、Microsoft Intune（以下、Intune）のようなMDMからも配布できます。
Windowsに組み込まれていないサードパーティ製アプリケーションのADMXも、Windowsデバイスに取り込んで使えます。

今回は、IntuneでサードパーティのADMXの設定をWindowsデバイスに配布する方法を紹介します。
それぞれの方法でWindowsデバイスに何が届き、レジストリに値が書き込まれるまでに何が起きるのかを、実機で確かめた結果とともに説明します。
題材には、ADMXが公開されているZoomのデスクトップアプリケーションを使います。

検証した環境は次のとおりです。

- Windows 11 Pro 25H2（ビルド26200.9457、ARM64の仮想マシン）。Microsoft 365 Business Premiumのライセンスにより、筆者の環境ではWindows 11 Businessと表示される。Microsoft Entra参加、Intuneに登録済み
- ZoomのADMX 7.2.0の`ZoomMeetings_HKLM.admx`（Zoomのサポート記事[Mass-deploying with Group Policy Objects](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0065466)で、バージョンごとに配布されているもの）

## Windowsデバイスで何が起きるのか

IntuneでADMXの設定を配布する方法には、設定カタログ、ADMXのインポート、カスタムプロファイル（OMA-URI）の3つがあります。
どの方法でも、Windowsデバイス側のしくみは同じです。
そこで、まずはWindowsデバイスで何が起きるのかを説明します。

### MDMクライアントとPolicy CSP

IntuneからWindowsデバイスへの設定は、OMA-DMというプロトコルで届きます。
受け取るのは、Windowsに組み込まれているMDMクライアントです。
[Mobile Device Management overview](https://learn.microsoft.com/en-us/windows/client-management/mdm-overview)にあるとおり、MDMサーバーがWindowsを管理するために、クライアントを別にインストールする必要はありません（構成プロファイルの場合。スクリプトの実行などには、別のエージェントが使われます）。

MDMクライアントは、受け取った設定を構成サービスプロバイダ（CSP: Configuration Service Provider）に渡します。
CSPも、Windowsに組み込まれている、設定の種類ごとの受け口です。
ポリシーを扱うのはPolicy CSPで、ほかにもBitLockerやVPNなど、機能ごとのCSPがあります。

```d2 title="Intuneから届いたOMA-URIと値を、Windowsに組み込まれたMDMクライアントが受け取ってPolicy CSPに渡し、Policy CSPがレジストリに書き込む流れ"
direction: down
intune: Intune {
  server: MDMサーバー {shape: image; icon: /d2-icons/server.svg}
}
client: Windowsデバイス {
  mdm: "MDMクライアント\n（Windowsに組み込み）" {shape: image; icon: /d2-icons/monitor-cog.svg}
  policy: Policy CSP {shape: image; icon: /d2-icons/cog.svg}
  other: "ほかのCSP\n（BitLockerなど）" {shape: image; icon: /d2-icons/cog.svg}
  reg: レジストリ {shape: image; icon: /d2-icons/database.svg}
  mdm -> policy
  mdm -> other
  policy -> reg
}
intune.server -> client.mdm: "OMA-URIと値"
```

どのCSPのどの設定に渡すかは、OMA-URIというパスで決まります。
OMA-URIは、ファイルシステムのパスのように、CSPの中の設定の住所を表します。
サードパーティのADMXでは、ADMXの取り込みも、取り込んだポリシーへの値の設定も、OMA-URIで指定します。
後述するZoomの例では、次の2つのOMA-URIを使います。

```text title="ZoomのADMXの取り込みと、取り込んだポリシーへの値の設定に使うOMA-URI"
./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomMeetings/Policy/ZoomMeetings_HKLM_7_2
./Device/Vendor/MSFT/Policy/Config/ZoomMeetings~Policy~ZoomUsCommunication~zoommeetings/DisableCloudRecording_Policy
```

それぞれのOMA-URIを区切りごとに分けると、次のようになります。

```d2 title="ADMXの取り込みのOMA-URIと、取り込んだADMXのポリシーに値を設定するOMA-URIを、区切りごとに分けてそれぞれの意味を示した図"
grid-rows: 2
grid-gap: 32
admx: ADMXの取り込み {
  shape: sql_table
  "./Device": 対象
  "/Vendor/MSFT/Policy": Policy CSP
  "/ConfigOperations/ADMXInstall": ADMXの取り込み
  "/ZoomMeetings": AppName
  "/Policy": 種類
  "/ZoomMeetings_HKLM_7_2": FileUid
}
value: 取り込んだADMXのポリシーへの値の設定 {
  shape: sql_table
  "./Device": 対象
  "/Vendor/MSFT/Policy": Policy CSP
  "/Config": ポリシーの設定
  "/ZoomMeetings": AppName
  "~Policy": 種類
  "~ZoomUsCommunication~zoommeetings": カテゴリのパス
  "/DisableCloudRecording_Policy": ポリシーの名前
}
```

図の区切りを上から順につなげると、元のOMA-URIになります。
値の設定のOMA-URIには、値として`<enabled/>`を送ります。

後述する設定カタログとADMXのインポートでは、IntuneがOMA-URIと値を生成して送ります。
カスタムプロファイルでは、OMA-URIと値の組を自分で書きます。

### ADMXの取り込みと値の設定

サードパーティ製アプリケーションのADMXは、Windowsに組み込まれていません。
そのため、Windowsデバイスは次の2段階で設定を受け取ります。

1. ADMXの取り込み：ADMXの全文をPolicy CSPに渡し、Windowsデバイスにポリシーの定義として登録する
2. 値の設定：取り込んだADMXのポリシーに、有効、無効や入力値を設定する

```d2 title="IntuneからADMXの全文と値が届き、Policy CSPがADMXを取り込んでから、値をADMXの定義に従ってレジストリに書き込む流れ"
grid-columns: 2
grid-gap: 64
intune: Intune {
  grid-rows: 2
  grid-gap: 32
  admx: "1. ADMXの全文" {shape: image; icon: /d2-icons/file-code.svg}
  value: "2. 値" {shape: image; icon: /d2-icons/file-digit.svg}
}
client: Windowsデバイス {
  grid-rows: 2
  grid-gap: 32
  csp: Policy CSP {shape: image; icon: /d2-icons/cog.svg}
  reg: レジストリ {shape: image; icon: /d2-icons/database.svg}
  csp -> reg
}
intune.admx -> client.csp: 取り込み
intune.value -> client.csp: 設定
```

ADMXの取り込みには、次のOMA-URIを使います。

```text title="ADMXを取り込むOMA-URI"
./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/{AppName}/Policy/{FileUid}
```

`{AppName}`はアプリケーションの名前、`{FileUid}`はADMXファイルの識別子で、どちらも取り込む側が決めます。
取り込んだADMXのポリシーには、次のOMA-URIで値を設定します。

```text title="取り込んだADMXのポリシーに値を設定するOMA-URI"
./Device/Vendor/MSFT/Policy/Config/{AppName}~Policy~{カテゴリのパス}/{ポリシーの名前}
```

`./Device`は`class="Machine"`のポリシーに使い、`class="User"`のポリシーでは`./User`にします。
`{カテゴリのパス}`は、ポリシーが属するカテゴリから`parentCategory`を親へたどり、親から順に`~`でつないだものです。
`{ポリシーの名前}`は、`policy`要素の`name`属性です。
どちらもエディタの表示名ではなく、ADMXの`name`を使います。

ZoomのADMXで、クラウドレコーディングを無効にするポリシーは次のように定義されています。

```xml title="ZoomMeetings_HKLM.admx（抜粋）" {2,4-6,8,10}
<categories>
  <category name="ZoomUsCommunication" displayName="$(string.ZoomUsCommunication)" />
  <category name="zoommeetings" displayName="$(string.zoommeetings)">
    <parentCategory ref="ZoomUsCommunication" />
  </category>
</categories>
<policies>
  <policy name="DisableCloudRecording_Policy" class="Machine"
    key="Software\Policies\Zoom\Zoom Meetings\Meetings" valueName="DisableCloudRecording" ...>
    <parentCategory ref="zoommeetings" />
    <enabledValue>
      <decimal value="1" />
    </enabledValue>
    <disabledValue>
      <decimal value="0" />
    </disabledValue>
  </policy>
</policies>
```

`DisableCloudRecording_Policy`のカテゴリは`zoommeetings`、その親は`ZoomUsCommunication`です。
AppNameを`ZoomMeetings`として取り込んだ場合、このポリシーのOMA-URIは次のようになります。

```text
./Device/Vendor/MSFT/Policy/Config/ZoomMeetings~Policy~ZoomUsCommunication~zoommeetings/DisableCloudRecording_Policy
```

値は、`<enabled/>`や`<disabled/>`のようなXMLの断片で指定します。
入力欄がある場合は、`elements`の`id`を使って`<data id="..." value="..."/>`を続けます。

```xml title="値の例"
<!-- 有効にする -->
<enabled/>
<!-- 無効にする -->
<disabled/>
<!-- 有効にして、数値の入力欄（id="SetUpdatingChannel_Part"）に1を入れる -->
<enabled/><data id="SetUpdatingChannel_Part" value="1"/>
```

### Windowsデバイスで確認できる場所

取り込みと値の設定は、Windowsデバイスの次の場所で確認できます。

| 確認できるもの | 場所 |
| --- | --- |
| 取り込んだADMXのファイル | `C:\ProgramData\Microsoft\PolicyManager\ADMXIngestion\<登録ID>\<AppName>\Policy\<FileUid>.admx` |
| 取り込んだポリシーの一覧 | `HKLM\SOFTWARE\Microsoft\PolicyManager\AdmxDefault\<登録ID>\<エリア名>` |
| 設定された値の状態 | `HKLM\SOFTWARE\Microsoft\PolicyManager\current\device\<エリア名>` |
| 処理の記録 | イベントビューアの「アプリケーションとサービス ログ > Microsoft > Windows > DeviceManagement-Enterprise-Diagnostics-Provider > Admin」 |

`<登録ID>`は、WindowsデバイスがIntuneに登録されたときのIDです。
`<エリア名>`は、OMA-URIの`{AppName}~Policy~{カテゴリのパス}`の部分です。

イベントログには、処理の種類ごとに決まったイベントIDが記録されます。
今回の検証で、ADMXの取り込みと値の設定に関係して記録されたのは、次のイベントIDです。

| イベントID | 内容 |
| --- | --- |
| 873 | ADMXの取り込みを開始 |
| 866 | ADMXを取り込んだ |
| 872 | 取り込み済みのADMXを更新 |
| 814 | ポリシーの値（文字列）を設定 |
| 819 | ポリシーの値を削除 |
| 454 | コマンドのエラー |

イベントIDは、Intuneの設定ごとに決まるものではなく、Windows側で処理の種類ごとに決まっているようです。
そのため、Intune以外のMDMから配布しても、同じ処理なら同じイベントIDが記録されると考えられます。
一方で、値の種類が違えば別のイベントIDになります。
たとえば、ADMXのポリシーのように文字列で設定する値は814ですが、整数で設定するWindows Updateのポリシーなどは813として記録されていました。
また、筆者が探した範囲では、Microsoftはこれらのイベントの一覧を公開していません。
Windowsのバージョンによって変わる可能性もあります。

次の画像は、イベントビューアで814のイベントを表示したところです。
AppNameを`ZoomTf`として取り込んだときの記録です。
ポリシーの名前（`DisableCloudRecording_Policy`）、エリア名（`ZoomTf~Policy~ZoomUsCommunication~zoommeetings`）、設定した文字列（`<enabled/>`）が記録されています。
登録IDとコンピュータ名は伏せています。

![イベントビューアでイベントID 814の一覧を表示し、DisableCloudRecording_Policyに<enabled/>を設定したイベントの詳細を開いた画面](/assets/posts/post/2026-10-13-1/event-viewer.png)

以降の検証結果は、これらの記録をもとにしています。

## IntuneでADMXの設定を配布する3つの方法

Intuneで、ADMXで定義された設定を配布する方法は次の3つです。

| 方法 | ADMXの用意 | 向いている場面 |
| --- | --- | --- |
| 設定カタログ | 不要（Intuneに組込み） | Microsoft EdgeやGoogle Chromeなど、Intuneがサポートしているアプリケーション |
| ADMXのインポート | Intuneの画面からアップロード | 設定カタログにないアプリケーション |
| カスタムプロファイル（OMA-URI） | プロファイルにADMXの全文を貼り付け | インポートの制限にあたる場合や、取り込みを細かく制御したい場合 |

Microsoftのドキュメントからは、設定カタログを優先するよう読み取れます。

- [Use ADMX templates on Windows devices in Microsoft Intune](https://learn.microsoft.com/en-us/intune/device-configuration/settings-catalog/configure-admx-templates-windows)の冒頭では、設定カタログの管理用テンプレートはIntuneに組み込まれており、ダウンロードやOMA-URIは不要と説明されています
- [Add custom settings for Windows devices in Microsoft Intune](https://learn.microsoft.com/en-us/intune/device-configuration/templates/configure-custom-settings-windows)の冒頭の注記では、設定できる項目は設定カタログで確認するよう案内されています
- [Import custom and third-party partner ADMX templates in Microsoft Intune](https://learn.microsoft.com/en-us/intune/device-configuration/settings-catalog/import-custom-admx-templates)の冒頭のヒントでも、Google Chromeなどの設定が設定カタログに組み込まれていると案内されています

設定カタログにないアプリケーションでは、ADMXのインポートか、カスタムプロファイルを使います。

## 設定カタログ

設定カタログは、Intuneにあらかじめ組み込まれた設定から選んで配布する方法です。
Microsoft Edgeのように、ADMXで管理するアプリケーションの設定も含まれています。

設定カタログのEdgeの設定も、Windowsデバイスでは同じようにADMXを取り込んでから値を設定していました。
「初回実行時のエクスペリエンスを非表示にする」（`HideFirstRunExperience`）を配布したところ、Windowsデバイスには次の2つのADMXが取り込まれました。

| AppName | FileUid | 内容 |
| --- | --- | --- |
| `microsoft_edge` | `HideFirstRunExperience` | このポリシー1つだけを含むADMX（2,364バイト） |
| `microsoft_edgev80diff` | `microsoft_edgev80diff` | 18個のポリシーを含むADMX |

1つ目は、Edgeの`msedge.admx`から、配布した設定だけを切り出したADMXでした。
Intuneは、Edgeの大きなADMXを丸ごと送るのではなく、必要な設定だけを取り込ませていることがわかります。
値は`HKLM\SOFTWARE\Policies\Microsoft\Edge\HideFirstRunExperience`に`1`として書き込まれました。

設定カタログにある設定は、ADMXの用意も取り込みの管理も不要です。

## ADMXのインポート

ADMXのインポートは、IntuneにADMXとADMLをアップロードし、その設定を「インポートされた管理用テンプレート」のプロファイルで配布する方法です。
執筆時点では、まだプレビューの機能です。

### 制限事項

[Import custom and third-party partner ADMX templates in Microsoft Intune](https://learn.microsoft.com/en-us/intune/device-configuration/settings-catalog/import-custom-admx-templates#what-you-need-to-know)の「What you need to know」には、次の制限が書かれています。

- アップロードできるADMXは20個まで。1ファイル1 MBまで
- 1つのADMXにつき、ADMLは1つ。言語は`en-US`だけ
- 入力欄に`comboBox`を使うADMXはインポートできない
- 別のADMXの名前空間を参照している場合は、参照先のADMXを先にアップロードする

名前空間は、ADMXがほかのADMXの定義を参照するときに使う名前です（[ADMXのしくみと読み方の「名前空間とカテゴリ」](/post/2026-10-05-1#名前空間とカテゴリ)を参照）。
ZoomのADMXは、`using`要素で`Windows.admx`の名前空間（`Microsoft.Policies.Windows`）を参照しています。
そのため、`Windows.admx`を先にアップロードする必要があります。

### ZoomのADMXをアップロードする

ZoomのADMXは、Zoomのサポート記事[Mass-deploying with Group Policy Objects](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0065466)から、バージョンごとのZIPファイルとしてダウンロードできます。
ZIPファイルの中の`ZoomMeetings_HKLM.admx`と`en-US\ZoomMeetings_HKLM.adml`を使います。

最初に`ZoomMeetings_HKLM.admx`をアップロードすると、次のエラーになりました。

```text
ADMX file referenced not found NamespaceMissing:Microsoft.Policies.Windows. Please upload it first.
```

先に`Windows.admx`と英語の`Windows.adml`をアップロードします。
ただし、筆者の日本語版のWindows 11では、`C:\Windows\PolicyDefinitions\en-US`が空で、英語の`Windows.adml`がありませんでした。
英語の`Windows.adml`は、Microsoftのダウンロードセンターで配布されている[Administrative Templates (.admx) for Windows 11 2025 Update (25H2)](https://www.microsoft.com/en-us/download/details.aspx?id=108394)から入手できます。
このMSIには、`Windows.admx`と`en-US\Windows.adml`が含まれています。
筆者はMacでMSIを展開したため、`staging_Windows.admx`と`staging_en_US_Windows.adml`という名前で取り出されたファイルを、`Windows.admx`と`en-US\Windows.adml`にリネームして使いました。

アップロードは、Intune管理センターの「デバイス > 構成 > ADMX のインポート」から行います。
`Windows.admx`、続いて`ZoomMeetings_HKLM.admx`をアップロードし、どちらも状態が「Available」になれば完了です。

### プロファイルを作成する

アップロードしたADMXの設定は、「Windows 10 以降」の「テンプレート > インポートされた管理用テンプレート (プレビュー)」のプロファイルで設定します。
今回は、次の2つの設定を有効にし、すべてのユーザーに割り当てました。

| 設定 | 値 |
| --- | --- |
| Client will disable and hide cloud recording feature | 有効 |
| Set the specified update channel when silent auto update is enabled | 有効、`1` |

### Windowsデバイスでの動き

Windowsデバイスで同期すると、まずZoomのADMXが取り込まれました。
AppNameとFileUidは、どちらも`fullarmor`にGUIDを付けた名前でした。

```text title="取り込まれたADMXのパス"
C:\ProgramData\Microsoft\PolicyManager\ADMXIngestion\<登録ID>\fullarmor<GUID>\Policy\fullarmor<GUID>.admx
```

`fullarmor`は、ZoomのADMXの`target`要素の`prefix`です。
GUIDは、Graph APIで確認したアップロードのIDと一致しました。
取り込まれたファイルを元のADMXと比べると、`prefix`が同じ`fullarmor<GUID>`に書き換えられ、XML宣言が削除されていました。
名前空間（`ZoomMeetings_HKLM_7_2`）は元のままです。

`Windows.admx`は取り込まれていませんでした。
Windowsに組み込まれているためだと考えられます。

値は、取り込みと同じ同期では届かず、次の同期で届きました。
イベントログには、OMA-URIで値を設定したときと同じ形式の814が記録されています。

```text title="値の設定（イベントID 814）"
ポリシー文字列の設定、ポリシー: (DisableCloudRecording_Policy)、領域: (fullarmor<GUID>~Policy~ZoomUsCommunication~zoommeetings)、…、文字列: (<enabled/>)
ポリシー文字列の設定、ポリシー: (SetUpdatingChannel_Policy)、領域: (fullarmor<GUID>~Policy~ZoomUsCommunication~zoomgeneral)、…、文字列: (<enabled/><data id="SetUpdatingChannel_Part" value="1" />)
```

レジストリには、次の値が書き込まれました。

- `HKLM\SOFTWARE\Policies\Zoom\Zoom Meetings\Meetings\DisableCloudRecording` = `1`
- `HKLM\SOFTWARE\Policies\Zoom\Zoom Meetings\General\SetUpdatingChannel` = `1`

インポートの機能は、OMA-URIのAppNameを`fullarmor<GUID>`に決めて、ADMXの全文と値をOMA-URIで送っていることがわかります。

### プロファイルを削除する

プロファイルを削除して同期すると、819で2つの値が削除されました。
`Meetings`と`General`のキーごと削除され、値は残りませんでした。

同じ同期で、取り込んだADMXもWindowsデバイスから削除されました。
Intune側にはADMXのアップロードを残したままです。
そのADMXを使うプロファイルがWindowsデバイスに割り当てられていなければ、取り込みも残さないようです。

## カスタムプロファイル（OMA-URI）

カスタムプロファイルでは、ADMXの取り込みと値の設定を、それぞれOMA-URIで書きます。
ADMXのインポートの制限にあたる場合や、AppNameなどを自分で決めたい場合に使います。

### ADMXを取り込む

「Windows 10 以降」の「テンプレート > カスタム」のプロファイルを作成し、OMA-URIの設定を追加します。

| 項目 | 値 |
| --- | --- |
| OMA-URI | `./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomMeetings/Policy/ZoomMeetings_HKLM_7_2` |
| データ型 | 文字列 |
| 値 | `ZoomMeetings_HKLM.admx`の全文 |

AppNameは`ZoomMeetings`、FileUidは`ZoomMeetings_HKLM_7_2`としました。
AppNameは値を設定するOMA-URIにも使うため、短くわかりやすい名前がよいと思います。

値の大きさには上限があります。
Microsoft Learnの[App Control for Businessのドキュメント](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/deployment/deploy-appcontrol-policies-using-intune)には、カスタムのOMA-URIで配布する値は350,000バイトまでと書かれています。
App Controlのドキュメントですが、この制限はカスタムのOMA-URI全般に当てはまるものとして書かれています。
Zoom 7.2.0の`ZoomMeetings_HKLM.admx`は335,280バイトで、上限に近い大きさです。
Google Chromeの`chrome.admx`のように、上限を超えるADMXもあります。

同期すると、ADMXは指定したAppNameとFileUidで取り込まれました。
ZoomのADMXは`Windows.admx`の名前空間を参照していますが、ADMXのインポートと違い、`Windows.admx`を用意する必要はありませんでした。
参照先の`Windows.admx`は、Windowsデバイスに組み込まれているものが使われると考えられます。
取り込まれたファイルは、文字コードがUTF-16に変わっていた以外は元のADMXのままで、ADMXのインポートのような書き換えはありませんでした。

### 値を設定する

値は、別のカスタムプロファイルに次の2行を追加しました。
データ型はどちらも「文字列」です。

| OMA-URI | 値 |
| --- | --- |
| `./Device/Vendor/MSFT/Policy/Config/ZoomMeetings~Policy~ZoomUsCommunication~zoommeetings/DisableCloudRecording_Policy` | `<enabled/>` |
| `./Device/Vendor/MSFT/Policy/Config/ZoomMeetings~Policy~ZoomUsCommunication~zoomgeneral/SetUpdatingChannel_Policy` | `<enabled/><data id="SetUpdatingChannel_Part" value="1"/>` |

同期すると、ADMXのインポートと同じ2つの値がレジストリに書き込まれました。

### プロファイルを削除する

値のプロファイルを削除すると、ADMXのインポートと同じように、819で値が削除されました。

一方で、取り込みのプロファイルを削除しても、取り込んだADMXはWindowsデバイスから削除されませんでした。
同期のたびに、次のエラーが記録されます。

```text title="取り込みの削除のエラー（イベントID 454）"
コマンドのエラー状態。…、CSP名: (Policy)、コマンドの種類: (Clear: first phase of Delete)、CSP URI: (./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomMeetings/Policy/ZoomMeetings_HKLM_7_2)、結果: (Unknown Win32 Error code: 0x86000011)
```

`0x86000011`は、そのノードではコマンドが許可されていないことを表すエラーです。
Policy CSPのドキュメントでは、ADMXInstallは`Delete`で削除できることになっています。
しかし、Intuneがカスタムプロファイルの削除で送る`Clear`は受け付けられないようです。

取り込んだADMXが残っても、値がなければレジストリには何も書き込まれません。
ただし、一度取り込んだAppNameとFileUidは、Windowsデバイスに残り続けると考えておく必要があります。

## 取り込みと値を1つのプロファイルにまとめる

カスタムプロファイルでは、ADMXの取り込みと値の設定を1つのプロファイルにまとめることもできます。
取り込みの行を先頭に置き、その後ろに値の行を並べます。

| OMA-URI | 値 |
| --- | --- |
| `./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomMeetingsAll/Policy/ZoomMeetings_HKLM_7_2` | `ZoomMeetings_HKLM.admx`の全文 |
| `./Device/Vendor/MSFT/Policy/Config/ZoomMeetingsAll~Policy~ZoomUsCommunication~zoommeetings/DisableCloudRecording_Policy` | `<enabled/>` |
| `./Device/Vendor/MSFT/Policy/Config/ZoomMeetingsAll~Policy~ZoomUsCommunication~zoomgeneral/SetUpdatingChannel_Policy` | `<enabled/><data id="SetUpdatingChannel_Part" value="1"/>` |

今回の検証では、最初の同期で取り込みと2つの値の設定が同じ秒に処理され、エラーもありませんでした。
ただし、プロファイルの中の行が上から順に処理されることは、ドキュメントでは保証されていません。
値の設定が取り込みより先に処理されると、その同期では値の設定がエラーになる可能性があります。
その場合は、次の同期で、取り込み済みのADMXのポリシーとして値が設定されると考えられます（今回は再現していません）。

1つのプロファイルにまとめると、ADMXと値の組み合わせを1ヵ所で管理できます。
AppNameを変えた場合に、値の行のOMA-URIを直し忘れることもありません。

## ADMXのインポートとOMA-URIを併用しない

ADMXのインポートでADMXを用意し、値だけをOMA-URIで設定することも考えられます。
インポートしたADMXは、Windowsデバイスでは`prefix`にGUIDを付けたAppName（Zoomの場合は`fullarmor<GUID>`）で取り込まれます。
そのため、次のようなOMA-URIで値を設定できる可能性があります。

```text
./Device/Vendor/MSFT/Policy/Config/fullarmor<GUID>~Policy~ZoomUsCommunication~zoommeetings/DisableCloudRecording_Policy
```

しかし、この併用は避けたほうがよいと考えています。
理由は次の3つです。

- ADMXをアップロードしただけでは、Windowsデバイスに取り込まれないと考えられる。プロファイルを削除すると取り込みも消えたことから、取り込まれるのは、そのADMXを使う「インポートされた管理用テンプレート」のプロファイルが割り当てられたときだけと思われる
- 取り込みが別のプロファイルに依存する。インポートの機能のプロファイルを外すと取り込みが削除され、OMA-URIで設定した値も効かなくなると考えられる
- AppNameのGUIDはアップロードのIDのため、バージョンの更新などでADMXをアップロードし直すと変わる。そのたびにOMA-URIを書き直す必要があると考えられる

この使い方はドキュメントにもありません。
ADMXの用意と値の設定は、ADMXのインポートかOMA-URIのどちらか一方にそろえるのが安全だと思います。

## どの方法を選ぶか

ここまでの結果をまとめると、次のようになります。

| | 設定カタログ | ADMXのインポート | OMA-URI |
| --- | --- | --- | --- |
| ADMXの用意 | 不要 | アップロード（`en-US`のADMLも必要） | プロファイルに全文を貼り付け |
| ADMXの大きさ | 該当なし（Intuneが用意） | 1 MBまで | 350,000バイトまで |
| AppName | Intuneが決める | `prefix`＋GUID | 自分で決める |
| 値の設定 | 画面で選ぶ | 画面で選ぶ | OMA-URIと値を自分で書く |
| 参照先のADMX（`Windows.admx`など） | 不要 | 先にアップロードが必要 | 不要 |
| プロファイルの削除 | 未検証 | 値と取り込みが消える | 値は消える。取り込みは残る |
| バージョンの更新 | Intuneの更新を待つ | プロファイルを削除してから入れ替えるか、別のバージョンとして追加する | 取り込みの行の中身を差し替える |

それぞれのメリットとデメリットは次のとおりです。

| 方法 | メリット | デメリット |
| --- | --- | --- |
| 設定カタログ | ADMXの用意もバージョンの管理も不要<br />画面で設定を選べる | 対応しているアプリケーションと設定しか使えない<br />新しいバージョンの設定を使えるのは、Intuneが対応してから |
| ADMXのインポート | 画面で設定を選べる<br />プロファイルを削除すると取り込みも消える | プレビューの機能<br />ADMXは1 MB、20個まで。ADMLは`en-US`だけで、`comboBox`は使えない<br />参照先の`Windows.admx`も、英語のADMLと一緒にアップロードが必要<br />ADMXを入れ替えるには、使っているプロファイルを先に削除する手順になっている<br />バージョンを並べて登録すると、プロファイルでは同じ名前の設定が並び、どのバージョンの設定か見分けにくい（筆者が画面で確認）<br />値は、取り込みの次の同期で届いた<br />新旧のバージョンのプロファイルを同時に割り当てると、値が消えることがある |
| OMA-URI | プレビューではない<br />ADMXのファイルをそのまま使える<br />参照先のADMXを用意しなくてよい<br />AppNameとFileUidを固定すれば、中身の差し替えでバージョンを更新できる<br />取り込みと値を1つのプロファイルにまとめると、1回の同期で反映できた | ADMXは350,000バイトまで<br />OMA-URIと値のXMLを手で書く必要があり、`./Device`と`./User`も書き分ける<br />書き間違いは管理センターでは検出されず、Windowsデバイスのイベントログで初めてわかる<br />取り込みのプロファイルを削除しても、取り込みは削除されない |

配布したい設定が設定カタログにあれば、設定カタログを使います。
設定カタログにない場合は、画面で設定を選べるADMXのインポートが扱いやすいと思います。
OMA-URIは、ADMXのインポートの制限にあたる場合や、AppNameを固定してバージョンの更新を管理したい場合に向いています。

## 終わりに

今回は、IntuneでサードパーティのADMXを配布する3つの方法を紹介しました。

どの方法でも、Windowsデバイスでは、Policy CSPがADMXを取り込み、その定義に従って値をレジストリに書き込みます。
違いは、ADMXの用意のしかた、AppNameを決める主体、そしてプロファイルを削除したときに取り込みが残るかどうかです。
前回の記事のようにADMXを読めれば、どの方法でも、どのレジストリの値が変わるのかを確かめられます。

ADMXのバージョンの更新や、Terraformでの管理、ADMXで書き込めない場所の設定については、[IntuneでADMXを運用する](/post/2026-10-13-2)で紹介します。
