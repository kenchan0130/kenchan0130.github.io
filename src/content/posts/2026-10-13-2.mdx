Microsoft Intune（以下、Intune）では、設定カタログやスクリプトなど、いくつかの方法でWindowsデバイスのレジストリに値を配布できます。
値は、一度配布して終わりではありません。
アプリケーションの新しいバージョンに合わせて設定を更新したり、配布する値を見直したりしながら運用していくことになります。
方法によって、更新のしやすさや、配布をやめたときに値が残るかどうかが違います。

今回は、Intuneでレジストリに値を配布する5つの方法を、運用の観点で比べます。
それぞれの方法で運用するときの注意点を、実機で確かめた結果とともに紹介します。
最後に、必須ではありませんが、あると管理が楽になるTerraformでの管理方法も紹介します。

検証した環境は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| OS | Windows 11 Pro 25H2（ビルド26200.9457）[^windows-business] |
| 端末 | ARM64の仮想マシン |
| 管理 | Microsoft Entra参加、Intuneに登録 |
| ライセンス | Microsoft 365 Business Premium |
| ADMX | ZoomのADMX 6.6.5と7.2.0の`ZoomMeetings_HKLM.admx`[^zoom-admx] |
| Terraformのプロバイダ | deploymenttheory/microsoft365 [1.4.0](https://github.com/deploymenttheory/terraform-provider-microsoft365/releases/tag/v1.4.0)、microsoft/msgraph [0.6.0](https://github.com/microsoft/terraform-provider-msgraph/releases/tag/v0.6.0)、terraprovider/microsoft365wp [0.20.0](https://github.com/terraprovider/terraform-provider-microsoft365wp/releases/tag/v0.20.0) |

[^windows-business]: Microsoft 365 Business Premiumのライセンスにより、今回の環境ではWindows 11 Businessと表示されます。
[^zoom-admx]: Zoomのサポート記事[Mass-deploying with Group Policy Objects](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0065466)から、バージョンごとのZIPファイルとしてダウンロードできます。

## Intuneでレジストリに値を配布する方法

Intuneでレジストリに値を配布する方法は、次の5つです。

| 方法 | しくみ | 書き込める場所 | 配布をやめたときの値 | ライセンス |
| --- | --- | --- | --- | --- |
| 1. 設定カタログ | Policy CSP | Intuneが対応している設定 | 削除される | Intuneのみ |
| 2. ADMXのインポート | Policy CSP | アップロードしたADMXの設定 | 削除される | Intuneのみ |
| 3. カスタムプロファイル（OMA-URI） | Policy CSP | 取り込んだADMXの設定 | 削除される | Intuneのみ |
| 4. プラットフォームスクリプト | Intune管理拡張機能 | 任意 | 残る | Intuneのみ |
| 5. 修復スクリプト | Intune管理拡張機能 | 任意 | 残る | Windows Enterprise E3、E5など |

方法1〜3は、ADMXのポリシーとして値を配布します。
Windowsに組み込まれたMDMクライアントが設定を受け取り、Policy CSPがADMXの定義に従ってレジストリに書き込みます。
しくみは、[前回の記事](/post/2026-10-14-1)で詳しく紹介しました。

方法4と5は、PowerShellのスクリプトでレジストリに直接書き込みます。
スクリプトは、Windowsデバイスに自動でインストールされるIntune管理拡張機能（IME: Intune Management Extension）が実行します。

### ADMXで書き込めないレジストリ

方法2と3でADMXを取り込む場合は、書き込める場所に制限があります。
[Win32 and Desktop Bridge app ADMX policy Ingestion](https://learn.microsoft.com/en-us/windows/client-management/win32-and-centennial-app-policy-configuration)によると、取り込んだADMXのポリシーは、次のキーの配下に書き込めません。

- `System`
- `Software\Microsoft`
- `Software\Policies\Microsoft`

例外として、`Software\Policies\Microsoft\Office`や`Software\Microsoft\Edge`など、書き込める場所も一覧で示されています。
たとえば、Visual Studio Code（以下、VS Code）はADMXを配布していますが、書き込み先の`Software\Policies\Microsoft\VSCode`は、執筆時点の例外の一覧にありません。

同じドキュメントには、取り込んだADMXで設定できない場合は、PowerShellのスクリプトなどでレジストリに直接書き込むよう書かれています。
設定カタログにもない設定で、書き込み先がこの制限にあたる場合は、方法4か5を使うことになります。

### Policy CSPで書き込んだ値は、配布をやめると削除される

[ADMXのしくみと読み方](/post/2026-10-05-1)では、グループポリシーを外しても値が残る「入れ墨」を紹介しました。
方法1〜3のPolicy CSPで書き込んだ値では、次のどの外し方でもポリシーの削除イベント（819）が記録され、値が削除されました。

| 外し方 | 確かめた方法 |
| --- | --- |
| プロファイルを削除する | 設定カタログ、ADMXのインポート、OMA-URI |
| プロファイルから値の行を外す | OMA-URI（有効、無効、数値の入力欄の値） |
| プロファイルの割り当てを外す | ADMXのインポート |
| `HKCU`のポリシーの値の行を外す | OMA-URI（`./User`） |

Policy CSPは、ポリシーが外されると、そのポリシーで書き込んだ値をADMXの定義に従って削除します。
そのため、方法1〜3では入れ墨を意識する必要は基本的にありません。
ただし、後述するように、ADMXのインポートでバージョンを更新するときは、この動きによって値まで消える場合があります。

一方で、方法4と5のスクリプトは、配布をやめても書き込んだ値を元に戻しません。
入れ墨への対策は、スクリプトの中に自分で用意する必要があります。

## 方法1：設定カタログ

設定カタログは、Intuneに組み込まれた設定から選んで配布する方法です。
Microsoft EdgeやGoogle Chromeなど、主要なアプリケーションのADMXの設定が含まれています。

運用の観点では、ADMXの用意も取り込みの管理もいらない点が大きいと思います。
アプリケーションの新しいバージョンでポリシーが増えても、Intuneが設定カタログに追加するのを待てば、ADMXを入れ替える作業は発生しません。
また、設定カタログのプロファイルは、配布する設定だけを小さなADMXに切り出して取り込ませるため、元のADMXの大きさを気にする必要もありません。

プロファイルを削除して同期すると、ポリシーの削除イベント（819）が記録され、値が削除されました。

ただ、設定カタログにあるのは、Intuneが対応している主要なアプリケーションの設定だけです。
対応していないアプリケーションや、まだ追加されていない新しいポリシーは、ほかの方法で配布する必要があります。

## 方法2：ADMXのインポート

ADMXのインポートは、IntuneにADMXとADMLをアップロードし、その設定を「インポートされた管理用テンプレート」のプロファイルで配布する方法です。
画面で設定を選べるため、OMA-URIや値のXMLを手で書く必要がありません。
プロファイルを削除すると、取り込んだADMXもWindowsデバイスから削除され、後に残りません。

執筆時点ではプレビューの機能で、次の制限があります。

- アップロードできるADMXは20個まで。1ファイル1 MBまで
- ADMLは`en-US`だけ
- 入力欄に`comboBox`を使うADMXはインポートできない
- 参照しているADMX（`Windows.admx`など）も、先にアップロードする必要がある

運用で特に注意が必要なのは、ADMXのバージョンの更新です。
[Import custom and third-party partner ADMX templates in Microsoft Intune](https://learn.microsoft.com/en-us/intune/device-configuration/settings-catalog/import-custom-admx-templates#replace-existing-admx-files)の「Replace existing ADMX files」には、インポート済みのADMXを更新する方法が2つ書かれています。

1. ADMXを使っているプロファイルとインポートしたADMXを削除してから、新しいADMXをインポートする
2. 名前空間を変えた新しいADMXを用意して、インポートする

1つ目の方法では、削除してからインポートし直すまでの間、値が配布されません。
ZoomのADMXはバージョンごとに名前空間が違う（6.6.5は`ZoomMeetings_HKLM_6_6`、7.2.0は`ZoomMeetings_HKLM_7_2`）ため、2つ目の方法で、6.6.5を残したまま7.2.0をアップロードできました。
しかし、2つのバージョンを並べて切り替えると、次の2つの問題がありました。

### 古いバージョンのプロファイルを削除すると、新しいバージョンの値も消える

次の流れで6.6.5から7.2.0に切り替えたところ、7.2.0のプロファイルで設定している値まで消えました。

1. 6.6.5のプロファイルで、3つの設定を有効にしている
2. 7.2.0のプロファイルを追加し、7.2.0にもある2つの設定を同じ値で有効にする
3. 6.6.5のプロファイルを削除して同期する
4. 6.6.5のポリシーについてポリシーの削除イベント（819）が3件記録され、3つの値がすべて削除される

それぞれの値は次のとおりです。
キーは、どれも`HKLM\SOFTWARE\Policies\Zoom\Zoom Meetings`の下です。

| 値 | 6.6.5のプロファイル | 7.2.0のプロファイル | 6.6.5のプロファイルを削除した後 |
| --- | --- | --- | --- |
| `Meetings\DisableCloudRecording` | `1` | `1` | 削除された |
| `General\SetUpdatingChannel` | `1` | `1` | 削除された |
| `Meetings\HideSelfView` | `1` | 設定なし | 削除された |

6.6.5と7.2.0は、Windowsデバイスでは別のAppNameで取り込まれ、別のポリシーとして扱われます。
6.6.5のポリシーを外すと、Policy CSPは6.6.5のポリシーで書き込んだ値を削除します。
7.2.0のポリシーも同じレジストリの値を書き込んでいますが、7.2.0のポリシーは「設定済み」のままのため、値は書き直されません。

さらに、Intune管理センターでは、7.2.0のプロファイルの状態は「成功」のままでした。
その後の同期でも、値は戻りませんでした。
管理センターでプロファイルを変更せずに保存しても、実際には保存されませんでした。
同じ値で設定を削除して追加し直しても、値は再送されませんでした。

この状態から7.2.0のプロファイルの値を設定し直すには、次の手順が必要でした。

1. 7.2.0のプロファイルの割り当てを外して同期する（ポリシーと取り込みが削除される）
2. 割り当て直して同期する（ADMXが取り込まれる）
3. もう一度同期する（値が設定される）

ADMXのインポートでバージョンを更新するときは、新旧のプロファイルが同じWindowsデバイスに同時に割り当たる状態を避けるのが安全だと思います。
古いバージョンのプロファイルを外したことを確認してから、新しいバージョンのプロファイルを割り当てると、この問題は避けられると考えられます。
ただし、この順番は試していません。
また、その間は値を配布できません。

### プロファイルの画面でバージョンを見分けられない

アップロードしたADMXの一覧では、「バージョン」の列に6.6と7.2が表示され、見分けられます。
この値は、ADMXの`policyDefinitions`要素の`revision`属性です。

一方で、プロファイルで設定を選ぶ画面には、ADMXのバージョンが表示されません。
2つのバージョンをアップロードした状態で設定を検索すると、同じ名前、同じパスの設定が2つずつ表示されました。
次の画像では、1行目と4行目、2行目と3行目が、それぞれ6.6.5と7.2.0の同じ設定です。
4行目を有効にしていますが、どちらのバージョンの設定なのかは画面からはわかりません。

![インポートされた管理用テンプレートのプロファイルでcloud recordingを検索し、同じ名前とパスの設定が2つずつ、合わせて4行表示されている画面](../../assets/posts/2026-10-13-2/duplicate-settings.png)

Graph APIで確かめても、2つの設定は、表示名、カテゴリのパス、ADMXのファイル名がすべて同じでした。
並べている期間が長くなると、どちらのバージョンの設定を編集しているのかがわからなくなります。
2つのバージョンを並べる場合は、プロファイルの名前にバージョンを含め、移行が終わったら古いバージョンのADMXを削除するのがよいと思います。

## 方法3：カスタムプロファイル（OMA-URI）

カスタムプロファイルでは、ADMXの取り込みと値の設定を、それぞれOMA-URIで書きます。
ADMXのインポートの制限（個数、言語、`comboBox`）にかからず、参照先の`Windows.admx`を用意しなくても取り込めます。
その代わり、OMA-URIと値のXMLを手で書く必要があり、書き間違いはWindowsデバイスに届くまでわかりません。
1つの値は350,000文字までのため、大きなADMXは取り込めません。

運用の観点で大きいのは、AppNameとFileUidを自分で決められる点です。
AppNameとFileUidを変えずに、取り込みの行の値だけを新しいバージョンのADMXに差し替えると、値を保ったまま更新できました。

### AppNameとFileUidを固定してバージョンを更新する

次の流れで、ZoomのADMXを6.6.5から7.2.0に更新しました。

1. AppNameを`ZoomUpg`、FileUidを`ZoomMeetings_HKLM`として、6.6.5のADMXを取り込む。どちらにもバージョンを含めない
2. 同じプロファイルで、3つのポリシーを有効にする
3. 取り込みの行の値を、7.2.0のADMXの全文に差し替えて同期する
4. ADMXの更新イベント（872）が記録され、値はそのまま残る
5. 7.2.0でなくなったポリシーの行を外して同期する
6. ポリシーの削除イベント（819）が記録され、その値だけが削除される

1.の取り込みのOMA-URIは、次のとおりです。

```text title="ZoomのADMXを取り込むOMA-URI"
./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomUpg/Policy/ZoomMeetings_HKLM
```

2.で有効にしたポリシーは、次の3つです。

| ポリシー | 内容 |
| --- | --- |
| `DisableCloudRecording_Policy` | クラウドレコーディングを無効にする |
| `SetUpdatingChannel_Policy` | 更新チャネルを指定する |
| `HideSelfView_Policy` | 自分のビデオを隠す。7.2.0のADMXにはない |

4.のADMXの更新イベント（872）は、次の内容で記録されました。

| 項目 | 内容 |
| --- | --- |
| AppName | `ZoomUpg` |
| 設定の種類 | `Policy` |
| FileUid | `ZoomMeetings_HKLM` |
| メッセージ | 以前の ADMX ファイルのインジェストでポリシー値が設定されました (0x1) |

取り込みは7.2.0に置き換わり、レジストリの値はそのまま残りました。
エリア名が変わらないので、値の行も直す必要はありません。
7.2.0のADMXにはない`HideSelfView_Policy`の値も、そのまま残りました。

5.で`HideSelfView_Policy`の行を外すと、`HideSelfView`だけが削除され、同じキーのほかの値は残りました。
新しいバージョンでなくなったポリシーは、値の行を外して削除します。

FileUidにバージョンを含めると、新しいバージョンでは別のFileUidになり、新旧の取り込みが並びます。
そうすると、ADMXのインポートと同じ問題が起きると考えられます。
さらに、[前回の記事](/post/2026-10-14-1)で紹介したように、OMA-URIで取り込んだADMXはプロファイルを削除しても消えません。
OMA-URIでは、AppNameとFileUidを固定して、中身だけを更新する運用が向いていると思います。

## 方法4：プラットフォームスクリプト

プラットフォームスクリプトは、PowerShellのスクリプトをWindowsデバイスで実行する機能です。
ADMXで書き込めない場所にも、レジストリの値を書き込めます。
追加のライセンスはいりません。

### プラットフォームスクリプトのしくみ

プラットフォームスクリプトは、構成プロファイルとは別のしくみで動きます。
構成プロファイルはWindowsのMDMクライアントがOMA-DMで受け取りますが、プラットフォームスクリプトはIMEがIntuneに問い合わせて受け取ります。

IMEは、プラットフォームスクリプトやWin32アプリなどを割り当てると、Windowsデバイスに自動でインストールされます。
Microsoft Entra参加などの条件を満たすWindowsデバイスが対象で、Windows Homeエディションと、Sモードでは動きません。
IMEは、Windowsのサービス（`IntuneManagementExtension`）として常駐します。

IMEがIntuneに問い合わせるのは、次のタイミングです。

- 8時間ごと
- Windowsデバイスの再起動や、IMEのサービスの再起動の後

[Understand Microsoft Intune Management Extension](https://learn.microsoft.com/en-us/intune/device-management/tools/management-extension-windows)には、IMEの問い合わせは、MDMクライアントの問い合わせとは独立していると書かれています。
今回の環境でも、Windowsの「設定」から同期しただけでは、スクリプトの変更は再起動するまで届きませんでした。

問い合わせで割り当てられたスクリプトを受け取ると、IMEは次のように実行します。

1. スクリプトを`C:\Program Files (x86)\Microsoft Intune Management Extension\Policies\Scripts`に保存する
2. `AgentExecutor.exe`が、Windows PowerShell（`powershell.exe`）を`-NoProfile -executionPolicy bypass -file <スクリプト>`で起動して実行する
3. 終了コードと出力をIntuneに報告する

今回の環境では、スクリプトのファイル名は`<ユーザーのID>_<スクリプトのID>.ps1`でした。
すべてのユーザーに割り当てたため、ユーザーごとに管理されているようです。
署名の確認を有効にしない場合は、実行ポリシーが`bypass`になるため、署名のないスクリプトも実行できます。

スクリプトの設定によって、実行のしかたが変わります。

| 設定（Terraformの属性） | 内容 |
| --- | --- |
| サインインしたユーザーの資格情報で実行する（`run_as_account`） | 画面のデフォルトは`user`（サインインしたユーザー）。`system`はSYSTEMとして実行する。`HKLM`に書き込むには`system`にする |
| 64ビットのPowerShellで実行する（`run_as_32_bit`） | 画面のデフォルトは32ビット。後述のとおり、書き込み先のキーが変わることがある |
| 署名の確認を強制する（`enforce_signature_check`） | 画面のデフォルトは有効で、信頼された発行元の署名が必要になる。署名しないスクリプトでは無効にする |

### 32ビットと64ビットのPowerShell

プラットフォームスクリプトは、Windows PowerShell 5.1で実行されます。
「64ビットのPowerShellで実行する」の設定によって、起動されるPowerShellが変わります。
今回の環境で、どちらの設定でもSYSTEMとして同じスクリプトを実行し、次の2つのキーに値を書き込みました。

- `HKLM:\SOFTWARE\IntuneBitnessTest`
- `HKLM:\SOFTWARE\Policies\IntuneBitnessTest`

結果は次のとおりです。

| 項目 | 32ビット（`run_as_32_bit = true`） | 64ビット（`run_as_32_bit = false`） |
| --- | --- | --- |
| PowerShellのパス | `C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe` | `C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe` |
| PowerShellのバージョン | 5.1.26100.9457 | 5.1.26100.9457 |
| `[Environment]::Is64BitProcess` | `False` | `True` |
| `PROCESSOR_ARCHITECTURE` | `x86` | `ARM64` |
| `HKLM:\SOFTWARE\IntuneBitnessTest`の書き込み先 | `HKLM\SOFTWARE\WOW6432Node\IntuneBitnessTest` | `HKLM\SOFTWARE\IntuneBitnessTest` |
| `HKLM:\SOFTWARE\Policies\IntuneBitnessTest`の書き込み先 | `HKLM\SOFTWARE\Policies\IntuneBitnessTest` | `HKLM\SOFTWARE\Policies\IntuneBitnessTest` |

32ビットでは、スクリプトに`HKLM:\SOFTWARE\IntuneBitnessTest`と書いても、実際には`WOW6432Node`の下に書き込まれました。
64ビットのアプリケーションは`WOW6432Node`の下を読まないため、意図した場所に値がないことになります。
一方で、`HKLM:\SOFTWARE\Policies`の下は、どちらの設定でも同じ場所に書き込まれました。
[Registry Keys Affected by WOW64](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys)では、`HKLM\SOFTWARE\Policies`は32ビットと64ビットで共有されるキーとされています。

画面のデフォルトは32ビットのため、`HKLM\SOFTWARE`の下に書き込むスクリプトでは、64ビットで実行するように変更する必要があります。

既存のスクリプトの設定を、あとから64ビットに変えた場合の動きも確かめました。
[Add PowerShell Scripts to Windows Devices in Microsoft Intune](https://learn.microsoft.com/en-us/intune/device-management/tools/run-powershell-scripts-windows)の表には、既存のスクリプトの設定を64ビットに変えた場合について、「the script opens (it doesn't run)」と書かれています。
しかし、今回の環境では、32ビットで実行に成功したスクリプトの設定だけを64ビットに変えると、IMEのログに記録されたポリシーのハッシュが変わりました。
スクリプトは、Windowsデバイスの再起動後に64ビットのPowerShellで再実行され、`HKLM\SOFTWARE\IntuneBitnessTest`に値が書き込まれました。

ただし、32ビットで実行したときに`WOW6432Node`の下に書き込んだ値は、そのまま残りました。
あとから64ビットに変えた場合は、32ビットで書き込んだ値を別に削除する必要があります。

なお、今回はARM64のWindowsで、32ビットのPowerShellはx86のエミュレーションで動きました。
x64のWindowsでは試していません。

### 一度成功したスクリプトは再実行されない

運用で特に注意が必要なのは、一度実行に成功したスクリプトが再実行されない点です。
IMEは、実行に成功したスクリプトを、スクリプトやポリシーが変わるまで再実行しません。
変わったかどうかは、スクリプトのハッシュで判断しているようです。
今回の検証でも、スクリプトの内容を変えてアップロードし直すと、IMEのログに次のように記録され、スクリプトが再実行されました。

```text title="IntuneManagementExtension.log（抜粋）"
[PowerShell] Policy id <スクリプトのID> for user <ユーザーのID> has different hash, reset download count. …
```

ハッシュが変わるため、コメントを一文字直しただけでも、割り当て先のすべてのWindowsデバイスで再実行されると考えられます。
反対に、内容を変えない限り、利用者や別のソフトウェアがレジストリの値を書き換えても、元に戻りません。
再実行されても問題がないように、スクリプトは何度実行しても同じ結果になるように書いておく必要があります。

失敗した場合（終了コードが0以外など）は、続く3回の問い合わせで再実行されます。
3回とも失敗すると、スクリプトが変わるまで実行されません。
また、スクリプトは200 KB未満にする必要があり、30分でタイムアウトします。
結果としてIntuneに報告されるのは、成功か失敗かと、スクリプトの出力だけです。

### スクリプトを削除しても値は残る

プラットフォームスクリプトを削除したときに、書き込んだ値がどうなるかを確かめました。
64ビットで次の2つの値を書き込んだスクリプトを、Intuneから削除しました。

- `HKLM\SOFTWARE\IntuneBitnessTest`
- `HKLM\SOFTWARE\Policies\IntuneBitnessTest`

Windowsデバイスを再起動してIMEが問い合わせると、IMEのログに次のように記録されました。

```text title="IntuneManagementExtension.log（抜粋）"
[PowerShell] Policy <スクリプトのID> for user <ユーザーのID> has been tombstoned. Cleaning up registry.
```

IMEは、スクリプトを管理するための自分のレジストリを片付けますが、スクリプトが書き込んだ2つの値は、どちらも残りました。

プラットフォームスクリプトで値を消したいときは、値を削除する処理をスクリプトに書いて実行してから、スクリプトを削除する必要があります。
後述するTerraformのスクリプトでは、書き込んだ値の一覧を記録し、一覧から外した値を削除するようにしました。

## 方法5：修復スクリプト

修復スクリプト（Remediations）は、検出スクリプトと修復スクリプトの組で、指定した間隔で検出スクリプトを実行します。
検出スクリプトが`exit 1`で終わったときだけ、修復スクリプトが実行されます。
プラットフォームスクリプトと違い、利用者や別のソフトウェアがレジストリの値を書き換えても、次の検出で元に戻せます。

[Use Remediations to Detect and Fix Support Issues](https://learn.microsoft.com/en-us/intune/device-management/tools/deploy-remediations)によると、ほかにも次の特徴があります。

- 実行の間隔は、1回だけ、1時間ごと（24時間未満の間隔）、毎日から選ぶ
- 検出スクリプトの出力（2,048文字まで）を、レポートやCSVで確認できる
- 特定のWindowsデバイスで、その場で実行できる（プレビュー）
- スクリプトのパッケージは200個まで
- 間隔を短くするとWindowsデバイスの負荷が増えるため、急がないものは間隔を長くするよう勧められている

修復スクリプトを使うには、利用者に次のいずれかのライセンスが必要です。

- Windows Enterprise E3、E5（Microsoft 365 F3、E3、E5に含まれる）
- Windows Education A3、A5（Microsoft 365 A3、A5に含まれる）
- Windows Virtual Desktop Access（VDA）

また、修復スクリプトもIMEが実行するスクリプトのため、プラットフォームスクリプトと同じく、配布をやめても書き込んだ値は元に戻りません。
入れ墨への対策は、スクリプトの中に自分で用意する必要があります。

今回の環境にはライセンスがないため、修復スクリプトは後述するTerraformの`terraform validate`での確認までにとどめています。

## どの方法を選ぶか

ここまでの結果を、運用の観点で比べると次のとおりです。

| 観点 | 1. 設定カタログ | 2. ADMXのインポート | 3. カスタムプロファイル | 4. プラットフォームスクリプト | 5. 修復スクリプト |
| --- | --- | --- | --- | --- | --- |
| 機能の状態 | 一般提供 | プレビュー | 一般提供 | 一般提供 | 一般提供 |
| 書き込める場所 | Intuneが対応している設定 | ADMXの制限の範囲 | ADMXの制限の範囲 | 任意 | 任意 |
| 設定のしかた | 画面で選ぶ | 画面で選ぶ | OMA-URIと値のXMLを手で書く | スクリプトを書く | 検出と修復のスクリプトを書く |
| バージョンの更新 | Intuneに任せる | 新旧を並べると値まで消える場合がある | AppNameとFileUidを固定すれば値を保ったまま更新できる | スクリプトを書き換える | スクリプトを書き換える |
| 配布をやめたときの値 | 削除される | 削除される | 削除される。取り込みは残る | 残る | 残る |
| 書き換えられた値 | 未検証 | 未検証 | 未検証 | 戻らない | 次の検出で戻せる |
| 結果の確認 | 設定ごとの状態 | 設定ごとの状態 | 行ごとの状態 | 成功か失敗かと出力 | 検出と修復の結果と出力 |
| ライセンス | Intuneのみ | Intuneのみ | Intuneのみ | Intuneのみ | Windows Enterprise E3、E5など |

選ぶ順番は、次のように考えるのがよいと思います。

1. 配布したい設定が設定カタログにあれば、設定カタログを使う
2. 設定カタログにない場合は、アプリケーションが配布しているADMXを使う。画面で選びたい場合はADMXのインポート、制限にあたる場合やバージョンの更新を安全に行いたい場合はカスタムプロファイル
3. ADMXで書き込めない場所や、ADMXが配布されていない設定は、プラットフォームスクリプトを使う
4. 書き換えられた値を戻したい場合で、ライセンスがあれば、修復スクリプトを使う

方法4と5を使う場合は、入れ墨への対策と、何度実行しても同じ結果になるスクリプトを用意する必要があります。

## プラスα：Terraformで管理する

ここまでの方法は、どれもIntune管理センターの画面で管理できます。
ただ、方法を組み合わせるほど、どの値をどの方法で配布しているのかを画面だけで追うのは難しくなります。
そこで、必須ではありませんが、プロファイルとスクリプトをTerraformで管理すると、運用が楽になると考えています。

Terraformで管理する利点は、次のとおりです。

- ADMXのファイル、OMA-URIの値、スクリプト、書き込む値の一覧を、1つのリポジトリでバージョン管理できる
- 変更をGitHubのPull Requestなどでレビューし、`plan`で差分を確かめてから反映できる
- 複数のテナントに、同じ設定を再現できる
- ADMXのバージョンの更新は、ファイルを差し替えて`apply`するだけになる
- 書き込む値の一覧からスクリプトを作ると、一覧を変えたときにスクリプトの内容が変わり、プラットフォームスクリプトが再実行される

次の点には注意が必要です。

- Intuneを扱うTerraformのプロバイダは、Graph APIのベータ版を使うものが多く、APIの変更の影響を受けることがある
- プロバイダの不具合にあたることがある。今回もdeploymenttheory/microsoft365で2件の不具合にあたった
- 画面で直接変更すると、Terraformの定義とずれる
- 強い権限を持つMicrosoft Entra IDのアプリケーションを管理する必要がある
- ADMXの全文がstateに入るため、stateが大きくなる

### プロバイダを選ぶ

Intuneを扱えるTerraformのプロバイダには、次の3つがあります。

| プロバイダ | 開発元 | 特徴 |
| --- | --- | --- |
| [deploymenttheory/microsoft365](https://github.com/deploymenttheory/terraform-provider-microsoft365) | コミュニティ | Intuneのリソースが多い。READMEには、パブリックプレビューで公式のサポートはないと書かれている |
| [terraprovider/microsoft365wp](https://github.com/terraprovider/terraform-provider-microsoft365wp) | コミュニティ | IntuneとMicrosoft Entra IDの設定を扱う |
| [microsoft/msgraph](https://github.com/microsoft/terraform-provider-msgraph) | Microsoft | Graph APIのリソースを、JSONを書いて汎用的に扱う |

この記事の5つの方法に対応するリソースは、次のとおりです。

| 方法 | deploymenttheory/microsoft365 | terraprovider/microsoft365wp | microsoft/msgraph |
| --- | --- | --- | --- |
| 1. 設定カタログ | `settings_catalog_configuration_policy` | `device_management_configuration_policy` | `msgraph_resource` |
| 2. ADMXのインポート | `group_policy_uploaded_definition_files`など | なし | `msgraph_resource` |
| 3. カスタムプロファイル | `windows_custom_configuration` | `device_configuration_custom` | `msgraph_resource` |
| 4. プラットフォームスクリプト | `windows_platform_script` | `device_management_script` | `msgraph_resource` |
| 5. 修復スクリプト | `windows_remediation_script` | なし | `msgraph_resource` |

deploymenttheory/microsoft365とterraprovider/microsoft365wpのリソース名は、それぞれ`microsoft365_graph_beta_device_management_`と`microsoft365wp_`で始まります。

今回は、5つの方法にすべて対応しているdeploymenttheory/microsoft365を中心に使いました。
microsoft/msgraphはMicrosoftが開発していますが、Graph APIのJSONをそのまま書くため、ほかの2つより記述が長くなります。
1つのプロバイダで足りないリソースや、不具合のあるリソースだけを、ほかのプロバイダで補うこともできます。

### 認証とプロバイダの設定

認証には、Microsoft Entra IDのアプリケーションを使います。
プロファイルの管理には`DeviceManagementConfiguration.ReadWrite.All`、スクリプトの管理には`DeviceManagementScripts.ReadWrite.All`のアプリケーションの権限が必要です。

deploymenttheory/microsoft365の設定は、環境変数でも指定できます。
1.4.0では、`M365_CLOUD`（またはプロバイダの`cloud`）を指定しないと、`plan`が「Invalid Microsoft Cloud Type」で失敗しました。

```sh
export M365_CLOUD=public
export M365_AUTH_METHOD=client_secret
export M365_TENANT_ID=...
export M365_CLIENT_ID=...
export M365_CLIENT_SECRET=...
```

terraprovider/microsoft365wpとmicrosoft/msgraphは、`ARM_TENANT_ID`、`ARM_CLIENT_ID`、`ARM_CLIENT_SECRET`の環境変数で認証できました。

### 設定カタログをTerraformで書く

設定カタログの設定は、設定の定義のID（`settingDefinitionId`）と値で書きます。
IDは、管理センターで作ったプロファイルをGraph APIで読むと確かめられます。
Microsoft Edgeの「Hide the First-run experience and splash screen」を有効にする例を、3つのプロバイダで書くと次のとおりです。

```hcl title="settings_catalog.tf（deploymenttheory/microsoft365）"
locals {
  edge_hide_first_run = "device_vendor_msft_policy_config_microsoft_edgev80diff~policy~microsoft_edge_hidefirstrunexperience"
}

resource "microsoft365_graph_beta_device_management_settings_catalog_configuration_policy" "edge" {
  name         = "tf-sc-deploymenttheory"
  platforms    = "windows10"
  technologies = ["mdm"]

  # 設定カタログのテンプレートを使わない場合も、空のまま指定する
  template_reference = {
    template_id = ""
  }

  configuration_policy = {
    settings = [
      {
        setting_instance = {
          odata_type            = "#microsoft.graph.deviceManagementConfigurationChoiceSettingInstance"
          setting_definition_id = local.edge_hide_first_run
          choice_setting_value = {
            value    = "${local.edge_hide_first_run}_1"
            children = []
          }
        }
      }
    ]
  }
}
```

```hcl title="settings_catalog.tf（terraprovider/microsoft365wp）"
resource "microsoft365wp_device_management_configuration_policy" "edge" {
  name         = "tf-sc-microsoft365wp"
  platforms    = "windows10"
  technologies = "mdm"

  settings = [
    {
      instance = {
        definition_id = local.edge_hide_first_run
        choice = {
          value = {
            value = "${local.edge_hide_first_run}_1"
          }
        }
      }
    }
  ]
}
```

```hcl title="settings_catalog.tf（microsoft/msgraph）"
resource "msgraph_resource" "edge" {
  url         = "deviceManagement/configurationPolicies"
  api_version = "beta"
  body = {
    name         = "tf-sc-msgraph"
    platforms    = "windows10"
    technologies = "mdm"
    settings = [
      {
        "@odata.type" = "#microsoft.graph.deviceManagementConfigurationSetting"
        settingInstance = {
          "@odata.type"       = "#microsoft.graph.deviceManagementConfigurationChoiceSettingInstance"
          settingDefinitionId = local.edge_hide_first_run
          choiceSettingValue = {
            value    = "${local.edge_hide_first_run}_1"
            children = []
          }
        }
      }
    ]
  }
}
```

3つとも同じ設定のプロファイルが作成され、続けて実行した`plan`は「No changes」でした。
deploymenttheory/microsoft365の1.4.0では、テンプレートを使わない場合も`template_reference`を指定しないと、「The argument "template_reference" is required」というエラーになりました。

### ADMXのインポートをTerraformで書く

ADMXのインポートは、次の3種類のリソースで書きます。

| リソース | 書くもの |
| --- | --- |
| `group_policy_uploaded_definition_files` | ADMXとADMLのアップロード |
| `group_policy_configuration` | プロファイル |
| `group_policy_definition` | プロファイルに含める設定 |

```hcl title="main.tf"
resource "microsoft365_graph_beta_device_management_group_policy_uploaded_definition_files" "zoom" {
  file_name = "ZoomMeetings_HKLM.admx"
  # ZoomのADMXとADMLはBOM付きのUTF-8で、BOMがあるとアップロードが失敗する
  content = trimprefix(file("${path.module}/files/ZoomMeetings_HKLM.admx"), "\ufeff")

  group_policy_uploaded_language_files = [
    {
      file_name     = "ZoomMeetings_HKLM.adml"
      language_code = "en-US"
      content       = trimprefix(file("${path.module}/files/en-US/ZoomMeetings_HKLM.adml"), "\ufeff")
    }
  ]
}

resource "microsoft365_graph_beta_device_management_group_policy_configuration" "zoom" {
  display_name = "imported-zoom"
}

resource "microsoft365_graph_beta_device_management_group_policy_definition" "zoom_disable_cloud_recording" {
  group_policy_configuration_id = microsoft365_graph_beta_device_management_group_policy_configuration.zoom.id
  policy_name                   = "Client will disable and hide cloud recording feature"
  class_type                    = "machine"
  category_path                 = "\\Zoom Meetings\\Zoom Meetings Settings"
  enabled                       = true

  depends_on = [microsoft365_graph_beta_device_management_group_policy_uploaded_definition_files.zoom]
}

resource "microsoft365_graph_beta_device_management_group_policy_definition" "zoom_update_channel" {
  group_policy_configuration_id = microsoft365_graph_beta_device_management_group_policy_configuration.zoom.id
  policy_name                   = "Set the specified update channel when silent auto update is enabled"
  class_type                    = "machine"
  category_path                 = "\\Zoom Meetings\\Zoom General Settings"
  enabled                       = true

  values = [
    {
      label = "Set the specified update channel when silent auto update is enabled"
      value = "1"
    }
  ]

  depends_on = [microsoft365_graph_beta_device_management_group_policy_uploaded_definition_files.zoom]
}
```

ZoomのADMXとADMLは、BOM付きのUTF-8です。
`file()`で読んだままアップロードすると、`Data at the root level is invalid. Line 1, position 1.`というエラーになります。
`trimprefix()`でBOMを取り除くと、アップロードできました。

`group_policy_definition`の`policy_name`と`category_path`には、ADMLの英語の表示名を使います。
ADMXの`name`ではない点に注意が必要です。

なお、1.3.0には、入力欄のない（有効、無効だけの）ポリシーを作成すると、作成後にstateから消えてしまう不具合がありました。
この不具合は筆者が送った[#4124](https://github.com/deploymenttheory/terraform-provider-microsoft365/pull/4124)で修正され、1.4.0に含まれています。
また、1.4.0の時点では、ADMXのアップロードのリソースは`terraform import`に対応していません。
プロファイルの設定の`terraform import`には、同じプロファイルに設定が2つ以上あると別の設定を取り込んでしまう不具合があり、[#4132](https://github.com/deploymenttheory/terraform-provider-microsoft365/pull/4132)で修正を提案しています。

### カスタムプロファイル（OMA-URI）をTerraformで書く

OMA-URIのカスタムプロファイルは、`windows_custom_configuration`で書きます。
取り込みと値の設定を、1つのプロファイルにまとめる形です。

```hcl title="main.tf"
resource "microsoft365_graph_beta_device_management_windows_custom_configuration" "zoom" {
  display_name = "omauri-zoom"

  assignments = [
    {
      type = "allLicensedUsersAssignmentTarget"
    }
  ]

  oma_settings = [
    {
      odata_type   = "#microsoft.graph.omaSettingString"
      display_name = "Zoom ADMX"
      oma_uri      = "./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomTf/Policy/ZoomMeetings_HKLM"
      value        = file("${path.module}/files/ZoomMeetings_HKLM.admx")
    },
    {
      odata_type   = "#microsoft.graph.omaSettingString"
      display_name = "Disable cloud recording"
      oma_uri      = "./Device/Vendor/MSFT/Policy/Config/ZoomTf~Policy~ZoomUsCommunication~zoommeetings/DisableCloudRecording_Policy"
      value        = "<enabled/>"
    },
  ]
}
```

OMA-URIの値は、BOM付きのままでも取り込めました。
BOMを取り除く必要があるのは、ADMXのインポートのアップロードだけです。

ADMXをファイルで管理し、`file()`で読み込むと、バージョンの更新はファイルを差し替えて`apply`するだけになります。
AppNameとFileUidは変わらないので、前述の、値を保ったまま更新する方法をそのまま使えます。

### プラットフォームスクリプトのテンプレート

プラットフォームスクリプトと修復スクリプトのために、書き込むレジストリの値をTerraformから渡す、汎用的なスクリプトを作りました。
方針は次のとおりです。

- 書き込む値の一覧をJSONで受け取り、Terraformの`templatefile()`でスクリプトに埋め込む
- 書き込んだ値の一覧をレジストリに記録し、次に実行したときに一覧から消えた値を削除する（入れ墨への対策）
- 削除する代わりに、デフォルト値（`default`）に戻すこともできる
- 型とデータがすでに同じ値は書き換えない
- 検出（`detect`）と適用（`apply`）の2つのモードを持ち、修復スクリプトにも使えるようにする

書き込む値は、次の形式で指定します。

```hcl
{
  path    = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode" # HKLM:\ か HKCU:\ で始まるキー
  name    = "UpdateMode"                                   # 値の名前
  type    = "String"                                       # String、ExpandString、MultiString、DWord、QWord
  value   = "manual"                                       # 書き込むデータ
  default = "default"                                      # 一覧から外したときに戻す値（省略すると値を削除）
}
```

スクリプトの全文は次のとおりです。
`${name}`、`${mode}`、`${settings_base64}`が、`templatefile()`で埋め込まれる変数です。

```powershell title="registry.ps1.tftpl"
# Applies registry values given by Terraform. Rendered with templatefile():
#   name             Identifier of this set of values, used to record what was written
#   mode             "apply" (platform script, remediation script) or "detect" (detection script)
#   settings_base64  base64encode(jsonencode(list of settings))
#
# A setting: { "path": "HKLM:\\SOFTWARE\\...", "name": "...", "type": "DWord", "value": 0, "default": 1 }
#   type     String, ExpandString, MultiString, DWord or QWord
#   default  Optional. Value to restore when the setting is removed from the list.
#            Without it, the value is deleted.

$ErrorActionPreference = 'Stop'

$Name = '${name}'
$Mode = '${mode}'
$SettingsBase64 = '${settings_base64}'

# Values this script wrote are recorded here, so that removed settings can be cleaned up.
# A script that runs as the signed-in user cannot write HKLM, so it records under HKCU.
if ([Security.Principal.WindowsIdentity]::GetCurrent().IsSystem) {
    $StateRoot = 'HKLM:\SOFTWARE\IntuneRegistrySettings'
} else {
    $StateRoot = 'HKCU:\SOFTWARE\IntuneRegistrySettings'
}

function Write-Log([string]$Message) {
    Write-Output "[$Name] $Message"
}

function Get-RegistryValueType([string]$Type) {
    $types = @{
        'String'       = [Microsoft.Win32.RegistryValueKind]::String
        'ExpandString' = [Microsoft.Win32.RegistryValueKind]::ExpandString
        'MultiString'  = [Microsoft.Win32.RegistryValueKind]::MultiString
        'DWord'        = [Microsoft.Win32.RegistryValueKind]::DWord
        'QWord'        = [Microsoft.Win32.RegistryValueKind]::QWord
    }
    if (-not $types.ContainsKey($Type)) {
        throw "Unsupported type '$Type'. Use String, ExpandString, MultiString, DWord or QWord."
    }
    return $types[$Type]
}

function ConvertTo-RegistryData($Value, [Microsoft.Win32.RegistryValueKind]$Kind) {
    switch ($Kind) {
        # Registry DWORD values are unsigned, but PowerShell writes them as Int32.
        'DWord'       { return [BitConverter]::ToInt32([BitConverter]::GetBytes([uint32][int64]$Value), 0) }
        'QWord'       { return [int64]$Value }
        'MultiString' { return [string[]]@($Value) }
        default       { return [string]$Value }
    }
}

# Returns $true when the value exists with the same type and data.
function Test-RegistryValue([string]$Path, [string]$ValueName, [Microsoft.Win32.RegistryValueKind]$Kind, $Data) {
    $key = Get-Item -LiteralPath $Path -ErrorAction SilentlyContinue
    if ($null -eq $key -or $key.GetValueNames() -notcontains $ValueName) {
        return $false
    }
    if ($key.GetValueKind($ValueName) -ne $Kind) {
        return $false
    }
    $current = $key.GetValue($ValueName, $null, 'DoNotExpandEnvironmentNames')
    if ($Kind -eq 'MultiString') {
        return (@($current) -join "`n") -ceq (@($Data) -join "`n")
    }
    return "$current" -ceq "$Data"
}

function Set-RegistryValue([string]$Path, [string]$ValueName, [Microsoft.Win32.RegistryValueKind]$Kind, $Data) {
    if (-not (Test-Path -LiteralPath $Path)) {
        New-Item -Path $Path -Force | Out-Null
    }
    New-ItemProperty -LiteralPath $Path -Name $ValueName -PropertyType $Kind -Value $Data -Force | Out-Null
}

# Windows PowerShell 5.1 returns a JSON array from ConvertFrom-Json as a single object.
# Passing it through the pipeline enumerates the elements.
function ConvertFrom-JsonArray([string]$Json) {
    return @(ConvertFrom-Json -InputObject $Json | ForEach-Object { $_ })
}

function Get-SettingKey($Setting) {
    return '{0}\{1}' -f $Setting.path, $Setting.name
}

try {
    if (@('apply', 'detect') -notcontains $Mode) {
        throw "Unsupported mode '$Mode'. Use apply or detect."
    }

    # A 32-bit process on 64-bit Windows writes HKLM:\SOFTWARE to WOW6432Node instead.
    if ([Environment]::Is64BitOperatingSystem -and -not [Environment]::Is64BitProcess) {
        throw 'Running as a 32-bit process. Set run_as_32_bit = false.'
    }

    $json = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($SettingsBase64))
    $settings = ConvertFrom-JsonArray $json

    $desired = [ordered]@{}
    foreach ($setting in $settings) {
        if ($setting.path -notmatch '^(HKLM|HKCU):\\') {
            throw "Path must start with HKLM:\ or HKCU:\ : '$($setting.path)'"
        }
        $kind = Get-RegistryValueType $setting.type
        $desired[(Get-SettingKey $setting)] = [pscustomobject]@{
            Setting = $setting
            Kind    = $kind
            Data    = ConvertTo-RegistryData $setting.value $kind
        }
    }

    # Settings written by the previous run.
    $statePath = Join-Path $StateRoot $Name
    $previous = @()
    $stateKey = Get-Item -LiteralPath $statePath -ErrorAction SilentlyContinue
    if ($null -ne $stateKey -and $stateKey.GetValueNames() -contains 'Settings') {
        $previous = ConvertFrom-JsonArray $stateKey.GetValue('Settings')
    }
    $removed = @($previous | Where-Object { -not $desired.Contains((Get-SettingKey $_)) })

    if ($Mode -eq 'detect') {
        $drift = @()
        foreach ($entry in $desired.Values) {
            if (-not (Test-RegistryValue $entry.Setting.path $entry.Setting.name $entry.Kind $entry.Data)) {
                $drift += Get-SettingKey $entry.Setting
            }
        }
        foreach ($setting in $removed) {
            $drift += '{0} (removed)' -f (Get-SettingKey $setting)
        }
        if ($drift.Count -gt 0) {
            Write-Log ('Not compliant: {0}' -f ($drift -join ', '))
            exit 1
        }
        Write-Log 'Compliant'
        exit 0
    }

    foreach ($entry in $desired.Values) {
        $key = Get-SettingKey $entry.Setting
        if (Test-RegistryValue $entry.Setting.path $entry.Setting.name $entry.Kind $entry.Data) {
            Write-Log "Unchanged: $key"
            continue
        }
        Set-RegistryValue $entry.Setting.path $entry.Setting.name $entry.Kind $entry.Data
        Write-Log "Set: $key"
    }

    foreach ($setting in $removed) {
        $key = Get-SettingKey $setting
        if ($null -ne $setting.default) {
            $kind = Get-RegistryValueType $setting.type
            Set-RegistryValue $setting.path $setting.name $kind (ConvertTo-RegistryData $setting.default $kind)
            Write-Log "Restored default: $key"
        } elseif ($null -ne (Get-ItemProperty -LiteralPath $setting.path -Name $setting.name -ErrorAction SilentlyContinue)) {
            Remove-ItemProperty -LiteralPath $setting.path -Name $setting.name
            Write-Log "Removed: $key"
        }
    }

    # Record what this run manages, for the next run.
    if (-not (Test-Path -LiteralPath $statePath)) {
        New-Item -Path $statePath -Force | Out-Null
    }
    $state = ConvertTo-Json -InputObject @($desired.Values | ForEach-Object { $_.Setting }) -Compress -Depth 5
    New-ItemProperty -LiteralPath $statePath -Name 'Settings' -PropertyType String -Value $state -Force | Out-Null

    Write-Log ('Applied {0} setting(s), cleaned up {1} removed setting(s)' -f $desired.Count, $removed.Count)
    exit 0
} catch {
    Write-Log "Failed: $($_.Exception.Message)"
    exit 1
}
```

いくつか補足します。

- JSONは`base64encode()`で埋め込んでいます。値に`'`が含まれていても、PowerShellの文字列が壊れないようにするためです
- 書き込んだ値の一覧は、SYSTEMで実行した場合は`HKLM:\SOFTWARE\IntuneRegistrySettings\<name>`に記録します
- 前述のとおり、32ビットのPowerShellでは`HKLM:\SOFTWARE\Policies`などを除き、`HKLM:\SOFTWARE`への書き込みが`WOW6432Node`に振り替えられます。書き込み先によって結果が変わらないように、32ビットで実行されたらエラーにしています
- Windows PowerShell 5.1の`ConvertFrom-Json`は、JSONの配列を1つのオブジェクトとして返します。そのまま`foreach`に渡すと要素に分かれないので、パイプラインを通して展開しています
- スクリプトのコメントとログは英語にしています。文字コードの違いで、Windows PowerShell 5.1が日本語を正しく読めない場合があるためです

このスクリプトは、Windows PowerShell 5.1で、値の追加、変更、削除、デフォルト値への復元、検出のそれぞれを確かめています。

### プラットフォームスクリプトをTerraformで書く

プラットフォームスクリプトは、`windows_platform_script`で書きます。
VS Codeの自動更新を手動にし、テレメトリーを無効にする例です。

```hcl title="registry.tf"
locals {
  vscode_registry_settings = [
    {
      path  = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name  = "UpdateMode"
      type  = "String"
      value = "manual"
    },
    {
      path  = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name  = "TelemetryLevel"
      type  = "String"
      value = "off"
    },
  ]
}

resource "microsoft365_graph_beta_device_management_windows_platform_script" "vscode_registry" {
  display_name = "vscode-registry"
  file_name    = "vscode-registry.ps1"
  script_content = templatefile("${path.module}/registry.ps1.tftpl", {
    name            = "vscode"
    mode            = "apply"
    settings_base64 = base64encode(jsonencode(local.vscode_registry_settings))
  })
  run_as_account          = "system"
  run_as_32_bit           = false
  enforce_signature_check = false

  assignments = [
    {
      type = "allLicensedUsersAssignmentTarget"
    }
  ]
}
```

`HKLM`に書き込めるように、`run_as_account`は`system`にします。
`run_as_32_bit`は`false`にして、64ビットのPowerShellで実行します。

`apply`してから約10分後、IMEがスクリプトを受け取り、SYSTEMとして実行しました。
IMEのログ（`C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AgentExecutor.log`）には、スクリプトの出力が記録されています。

```text title="AgentExecutor.log（抜粋）"
[vscode] Set: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\UpdateMode
[vscode] Set: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\TelemetryLevel
[vscode] Applied 2 setting(s), cleaned up 0 removed setting(s)
```

`HKLM\SOFTWARE\Policies\Microsoft\VSCode`に、`UpdateMode`（`manual`）と`TelemetryLevel`（`off`）が書き込まれました。

次に、Terraformで`TelemetryLevel`を一覧から外し、`UpdateMode`を`none`に変えて`apply`しました。
`UpdateMode`には、一覧から外したときに戻すデフォルト値として`default`を指定しています。

```hcl title="registry.tf" ins={7-8} del={10-15}
locals {
  vscode_registry_settings = [
    {
      path    = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name    = "UpdateMode"
      type    = "String"
      value   = "none"
      default = "default"
    },
    {
      path  = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name  = "TelemetryLevel"
      type  = "String"
      value = "off"
    },
  ]
}
```

`apply`から約5分後にWindowsデバイスを再起動すると、前述のとおり、IMEはスクリプトのハッシュが変わったことを検出し、スクリプトを再実行しました。

```text title="AgentExecutor.log（抜粋）"
[vscode] Set: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\UpdateMode
[vscode] Removed: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\TelemetryLevel
[vscode] Applied 1 setting(s), cleaned up 1 removed setting(s)
```

`UpdateMode`は`none`に変わり、一覧から外した`TelemetryLevel`は削除されました。
値の一覧を変えると、`templatefile()`で埋め込んだスクリプトの内容が変わるため、IMEが再実行します。
値を消したいときは、スクリプトを削除する前に一覧から外して`apply`し、Windowsデバイスで削除されたことを確認します。

### 修復スクリプトをTerraformで書く

前述のスクリプトは、`mode`を`detect`にすると、値が一覧と違う場合に`exit 1`で終わります。
同じテンプレートから、検出スクリプトと修復スクリプトの2つを作れます。

```hcl title="remediation.tf"
locals {
  vscode_registry_script = {
    name            = "vscode"
    settings_base64 = base64encode(jsonencode(local.vscode_registry_settings))
  }
}

resource "microsoft365_graph_beta_device_management_windows_remediation_script" "vscode_registry" {
  display_name   = "vscode-registry"
  publisher      = "IT"
  run_as_account = "system"
  run_as_32_bit  = false

  detection_script_content   = templatefile("${path.module}/registry.ps1.tftpl", merge(local.vscode_registry_script, { mode = "detect" }))
  remediation_script_content = templatefile("${path.module}/registry.ps1.tftpl", merge(local.vscode_registry_script, { mode = "apply" }))

  assignments = [
    {
      type = "allLicensedUsersAssignmentTarget"
      daily_schedule = {
        interval = 1
        time     = "09:00:00"
        use_utc  = false
      }
    },
  ]
}
```

検出と修復の動きは、Windows PowerShell 5.1でスクリプトを直接実行して確かめました。

## 終わりに

今回は、Intuneでレジストリに値を配布する5つの方法を、運用の観点で比べました。

設定カタログ、ADMXのインポート、カスタムプロファイルは、Policy CSPが値を書き込み、配布をやめると値が削除されます。
ただし、ADMXのインポートで新旧のバージョンを並べると、古いバージョンのポリシーの削除で、新しいバージョンの値まで消えることがありました。
カスタムプロファイルなら、AppNameとFileUidを固定して中身だけを差し替えると、値を保ったまま更新できました。

ADMXで書き込めない場所は、プラットフォームスクリプトや修復スクリプトで書き込めます。
ただし、値の削除や、書き換えられた値を戻す処理は、自分で用意する必要があります。
Terraformで値の一覧とスクリプトをまとめて管理すると、こうした処理を1つのスクリプトに閉じ込められると思います。
