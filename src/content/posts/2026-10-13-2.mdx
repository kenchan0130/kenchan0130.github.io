前回の[IntuneでサードパーティのADMXを配布する](/post/2026-10-13-1)では、Microsoft Intune（以下、Intune）でADMXの設定を配布する3つの方法を紹介しました。
配布できるようになると、次に困るのは運用です。
アプリケーションの新しいバージョンでADMXが更新されたり、配布をやめた設定の値が残ったりします。

今回は、IntuneでADMXを運用するときの次の話題を、実機で確かめた結果とともに紹介します。

- ADMXのバージョンの更新
- 入れ墨（設定をやめた値が残る問題）
- Terraformでの管理
- ADMXで書き込めないレジストリへの対処

検証した環境は、前回と同じWindows 11 Pro 25H2（ビルド26200.9457、ARM64の仮想マシン、Microsoft 365 Business Premiumのライセンスにより、Windows 11 Businessとして表示される）です。
Terraformのプロバイダは、deploymenttheory/microsoft365の1.4.0を使いました。

## ADMXのバージョンを更新する

アプリケーションの新しいバージョンでは、ADMXにポリシーが追加されたり、削除されたりします。
ZoomのADMXを6.6.5から7.2.0に更新する例で、ADMXのインポートとOMA-URIのそれぞれで確かめました。

### ADMXのインポートでの更新

Microsoft Learnには、インポート済みのADMXを更新する方法が2つ書かれています。

1. ADMXを使っているプロファイルとインポートしたADMXを削除してから、新しいADMXをインポートする
2. 名前空間を変えた新しいADMXを用意して、インポートする

ZoomのADMXは、バージョンごとに名前空間が違います（6.6.5は`ZoomMeetings_HKLM_6_6`、7.2.0は`ZoomMeetings_HKLM_7_2`）。
そのため、6.6.5を残したまま7.2.0をアップロードでき、2つのバージョンが共存しました。

問題は、プロファイルの切り替えです。
次の順番で切り替えたところ、Windowsデバイスの値が消えました。

1. 6.6.5のプロファイルで、クラウドレコーディングの無効化と更新チャネルを設定している
2. 7.2.0のプロファイルを作成して、同じ2つの設定を割り当てる
3. 6.6.5のプロファイルを削除する

3.の同期で、6.6.5のポリシーの削除（819）が記録され、`HKLM\SOFTWARE\Policies\Zoom\Zoom Meetings`の下の値がキーごと削除されました。
7.2.0のプロファイルも同じレジストリの値を設定しているはずですが、値は戻りませんでした。

6.6.5と7.2.0は、Windowsデバイスでは別のAppNameで取り込まれ、別のポリシーとして扱われます。
6.6.5のポリシーを削除すると、ADMXの定義に従ってレジストリの値も削除されます。
7.2.0のポリシーは「設定済み」のままですので、値は書き直されません。

さらに、Intune管理センターでは、7.2.0のプロファイルの状態は「成功」のままでした。
その後の同期でも、値は戻りませんでした。
管理センターでプロファイルを変更せずに保存しても、実際には保存されませんでした。
同じ値で設定を削除して追加し直しても、値は再送されませんでした。

値を戻せたのは、次の手順です。

1. 7.2.0のプロファイルの割り当てを外して同期する（ポリシーと取り込みが削除される）
2. 割り当て直して同期する（ADMXが取り込まれる）
3. もう一度同期する（値が設定される）

ADMXのインポートでバージョンを更新するときは、新旧のプロファイルが同じWindowsデバイスに同時に割り当たる状態を避けるのが安全だと思います。
古いバージョンのプロファイルを外したことを確認してから、新しいバージョンのプロファイルを割り当てると、この問題は避けられると考えられます（この順番は未検証です）。
ただし、その間は設定のない時間ができます。

### OMA-URIでの更新

OMA-URIでは、AppNameとFileUidを変えずに、取り込みの行の値だけを新しいバージョンのADMXに差し替えると、安全に更新できました。

そのため、FileUidにはバージョンを含めない名前（`ZoomMeetings_HKLM`など）を付けておきます。

```text title="バージョンを含めないAppNameとFileUid"
./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomUpg/Policy/ZoomMeetings_HKLM
```

6.6.5のADMXで取り込み、クラウドレコーディングの無効化、更新チャネル、7.2.0ではなくなった`HideSelfView_Policy`の3つの値を設定しておきます。
その後で、取り込みの行の値を7.2.0のADMXに差し替えて同期すると、イベントID 872が記録されました。

```text title="取り込み済みのADMXの更新（イベントID 872）"
ADMX インジェストで既存の Admx インジェストの更新を開始しています。…、アプリ名 (ZoomUpg)、設定の種類 (Policy)、一意の ID (ZoomMeetings_HKLM)、以前の ADMX ファイルのインジェストでポリシー値が設定されました (0x1)。
```

取り込みは7.2.0に置き換わり、レジストリの値はそのまま残りました。
エリア名が変わらないので、値の行も直す必要はありません。

7.2.0のADMXにはない`HideSelfView_Policy`の値も、そのまま残りました。
この行をプロファイルから外すと、819で`HideSelfView`だけが削除され、同じキーのほかの値は残りました。
新しいバージョンでなくなったポリシーは、値の行を外して削除します。

OMA-URIでも、AppNameやFileUidを変えて新旧を並べると、ADMXのインポートと同じ問題が起きると考えられます。
さらに、前回紹介したように、OMA-URIで取り込んだADMXはプロファイルを削除しても消えません。
OMA-URIでは、AppNameとFileUidを固定して、中身だけを更新する運用が向いていると思います。

## 入れ墨

[ADMXのしくみと読み方](/post/2026-10-05-1)では、ポリシーを外しても値が残る「入れ墨」を紹介しました。
IntuneのPolicy CSPで書き込んだ値でも入れ墨が起きるのかを、次の条件で確かめました。

| 外し方 | 対象 |
| --- | --- |
| プロファイルを削除する | ADMXのインポート、OMA-URI |
| プロファイルから値の行を外す | 有効、無効、数値の入力欄の値 |
| プロファイルの割り当てを外す | ADMXのインポート |
| `HKCU`のポリシーの値の行を外す | OMA-URI（`./User`） |

`HKCU`のポリシーでも、ADMXの取り込みは`./Device`の`ADMXInstall`で行い、値の設定だけを`./User`にします。

どの条件でも、値は819で削除され、入れ墨は起きませんでした。
`Software\Policies`の配下に書き込むポリシーで、Policy CSPが自分で書き込んだ値であれば、外したときに削除されるようです。

注意が必要なのは、ADMXのインポートでバージョンを更新したときのように、別のポリシーの削除で値が消える場合です。
また、後述するスクリプトでレジストリに書き込む方法では、入れ墨への対策を自分で書く必要があります。

## Terraformで管理する

IntuneのプロファイルをTerraformで管理するには、コミュニティで開発されている[deploymenttheory/microsoft365](https://registry.terraform.io/providers/deploymenttheory/microsoft365/latest)プロバイダを使えます。
Microsoftの公式のプロバイダではありません。

認証には、Microsoft Entra IDのアプリケーションを使います。
プロファイルの管理には`DeviceManagementConfiguration.ReadWrite.All`、後述するスクリプトの管理には`DeviceManagementScripts.ReadWrite.All`のアプリケーションの権限が必要です。

プロバイダの設定は、環境変数でも指定できます。
1.4.0では、`M365_CLOUD`（またはプロバイダの`cloud`）を指定しないと、`plan`が「Invalid Microsoft Cloud Type」で失敗しました。

```sh
export M365_CLOUD=public
export M365_AUTH_METHOD=client_secret
export M365_TENANT_ID=...
export M365_CLIENT_ID=...
export M365_CLIENT_SECRET=...
```

### ADMXのインポート

ADMXのインポートは、ADMXとADMLのアップロード、プロファイル、プロファイルの設定の3種類のリソースで書きます。

```hcl title="main.tf"
resource "microsoft365_graph_beta_device_management_group_policy_uploaded_definition_files" "zoom" {
  file_name = "ZoomMeetings_HKLM.admx"
  # ZoomのADMXとADMLはBOM付きのUTF-8で、BOMがあるとアップロードが失敗する
  content = trimprefix(file("${path.module}/files/ZoomMeetings_HKLM.admx"), "\ufeff")

  group_policy_uploaded_language_files = [
    {
      file_name     = "ZoomMeetings_HKLM.adml"
      language_code = "en-US"
      content       = trimprefix(file("${path.module}/files/en-US/ZoomMeetings_HKLM.adml"), "\ufeff")
    }
  ]
}

resource "microsoft365_graph_beta_device_management_group_policy_configuration" "zoom" {
  display_name = "imported-zoom"
}

resource "microsoft365_graph_beta_device_management_group_policy_definition" "zoom_disable_cloud_recording" {
  group_policy_configuration_id = microsoft365_graph_beta_device_management_group_policy_configuration.zoom.id
  policy_name                   = "Client will disable and hide cloud recording feature"
  class_type                    = "machine"
  category_path                 = "\\Zoom Meetings\\Zoom Meetings Settings"
  enabled                       = true

  depends_on = [microsoft365_graph_beta_device_management_group_policy_uploaded_definition_files.zoom]
}

resource "microsoft365_graph_beta_device_management_group_policy_definition" "zoom_update_channel" {
  group_policy_configuration_id = microsoft365_graph_beta_device_management_group_policy_configuration.zoom.id
  policy_name                   = "Set the specified update channel when silent auto update is enabled"
  class_type                    = "machine"
  category_path                 = "\\Zoom Meetings\\Zoom General Settings"
  enabled                       = true

  values = [
    {
      label = "Set the specified update channel when silent auto update is enabled"
      value = "1"
    }
  ]

  depends_on = [microsoft365_graph_beta_device_management_group_policy_uploaded_definition_files.zoom]
}
```

ZoomのADMXとADMLは、BOM付きのUTF-8です。
`file()`で読んだままアップロードすると、`Data at the root level is invalid. Line 1, position 1.`というエラーになります。
`trimprefix()`でBOMを取り除くと、アップロードできました。

`group_policy_definition`の`policy_name`と`category_path`には、ADMLの英語の表示名を使います。
ADMXの`name`ではない点に注意が必要です。

なお、1.3.0には、入力欄のない（有効、無効だけの）ポリシーを作成すると、作成後にstateから消えてしまう不具合がありました。
この不具合は筆者が送った[#4124](https://github.com/deploymenttheory/terraform-provider-microsoft365/pull/4124)で修正され、1.4.0に含まれています。
また、1.4.0の時点では、ADMXのアップロードのリソースは`terraform import`に対応していません。
プロファイルの設定の`terraform import`には、同じプロファイルに設定が2つ以上あると別の設定を取り込んでしまう不具合があり、[#4132](https://github.com/deploymenttheory/terraform-provider-microsoft365/pull/4132)で修正を提案しています。

### OMA-URI

OMA-URIのカスタムプロファイルは、`windows_custom_configuration`で書きます。
前回紹介した、取り込みと値を1つのプロファイルにまとめる形です。

```hcl title="main.tf"
resource "microsoft365_graph_beta_device_management_windows_custom_configuration" "zoom" {
  display_name = "omauri-zoom"

  assignments = [
    {
      type = "allLicensedUsersAssignmentTarget"
    }
  ]

  oma_settings = [
    {
      odata_type   = "#microsoft.graph.omaSettingString"
      display_name = "Zoom ADMX"
      oma_uri      = "./Device/Vendor/MSFT/Policy/ConfigOperations/ADMXInstall/ZoomTf/Policy/ZoomMeetings_HKLM"
      value        = file("${path.module}/files/ZoomMeetings_HKLM.admx")
    },
    {
      odata_type   = "#microsoft.graph.omaSettingString"
      display_name = "Disable cloud recording"
      oma_uri      = "./Device/Vendor/MSFT/Policy/Config/ZoomTf~Policy~ZoomUsCommunication~zoommeetings/DisableCloudRecording_Policy"
      value        = "<enabled/>"
    },
  ]
}
```

OMA-URIの値は、BOM付きのままでも取り込めました。
BOMを取り除く必要があるのは、ADMXのインポートのアップロードだけです。

ADMXをファイルで管理し、`file()`で読み込むと、バージョンの更新はファイルを差し替えて`apply`するだけになります。
AppNameとFileUidは変わらないので、前述の安全な更新方法をそのまま使えます。

## ADMXで書き込めないレジストリ

ADMXの取り込みには、書き込める場所の制限があります。
Microsoft Learnの[Win32 and Desktop Bridge app ADMX policy Ingestion](https://learn.microsoft.com/en-us/windows/client-management/win32-and-centennial-app-policy-configuration)によると、取り込んだADMXのポリシーは、次のキーの配下に書き込めません。

- `System`
- `Software\Microsoft`
- `Software\Policies\Microsoft`

ただし、`Software\Policies\Microsoft\Office`や`Software\Microsoft\Edge`など、例外として書き込める場所が一覧で示されています。
この制限は、ADMXのインポートとOMA-URIのどちらにも当てはまります。

### Visual Studio Codeの例

Visual Studio Code（以下、VS Code）は、ADMXを配布しています。
書き込み先は`Software\Policies\Microsoft\VSCode`で、2025-11-20に更新されたLearnの例外の一覧にはありません。
VS Codeのリポジトリでも、Intuneで取り込めない問題が報告されています（[#242922](https://github.com/microsoft/vscode/issues/242922)、[#281840](https://github.com/microsoft/vscode/issues/281840)）。

今回の環境（ビルド26200.9457）では、OMA-URIでVS Code 1.141.0のADMXを取り込み、`EnableFeedback`の値を書き込めました。
しかし、これはドキュメントに書かれていない動きです。
Windowsの更新で変わる可能性もあるので、例外の一覧にない場所はADMXでは書き込めないものとして扱うのがよいと思います。

Learnのドキュメントには、取り込んだADMXで設定できない場合は、PowerShellのスクリプトなどでレジストリに直接書き込むよう書かれています。

## スクリプトでレジストリに書き込む

Intuneでは、PowerShellのスクリプトをプラットフォームスクリプトとして配布できます。
スクリプトは、Windowsデバイスに自動でインストールされるIntune管理拡張機能（IME: Intune Management Extension）が実行します。

### プラットフォームスクリプトのしくみ

プラットフォームスクリプトは、構成プロファイルとは別のしくみで動きます。
構成プロファイルはWindowsのMDMの機能がOMA-DMで受け取りますが、プラットフォームスクリプトはIMEがIntuneに問い合わせて受け取ります。

IMEは、プラットフォームスクリプトやWin32アプリなどを割り当てると、Windowsデバイスに自動でインストールされます。
Microsoft Entra参加などの条件を満たすWindowsデバイスが対象で、Windows Homeエディションと、Sモードでは動きません。
IMEは、Windowsのサービス（`IntuneManagementExtension`）として常駐します。

IMEがIntuneに問い合わせるのは、次のタイミングです。

- 8時間ごと
- Windowsデバイスの再起動や、IMEのサービスの再起動の後
- Windowsの「設定」やIntune管理センターから同期したとき

問い合わせで割り当てられたスクリプトを受け取ると、IMEは次のように実行します。

1. スクリプトを`C:\Program Files (x86)\Microsoft Intune Management Extension\Policies\Scripts`に保存する
2. `AgentExecutor.exe`が、Windows PowerShell（`powershell.exe`）を`-NoProfile -executionPolicy bypass -file <スクリプト>`で起動して実行する
3. 終了コードと出力をIntuneに報告する

今回の環境では、スクリプトのファイル名は`<ユーザーのID>_<スクリプトのID>.ps1`でした。
すべてのユーザーに割り当てたため、ユーザーごとに管理されているようです。
署名の確認を有効にしない場合は、実行ポリシーが`bypass`になるため、署名のないスクリプトも実行できます。

スクリプトの設定によって、実行のしかたが変わります。

| 設定（Terraformの属性） | 内容 |
| --- | --- |
| サインインしたユーザーの資格情報で実行する（`run_as_account`） | 画面のデフォルトは`user`（サインインしたユーザー）。`system`はSYSTEMとして実行する。`HKLM`に書き込むには`system`にする |
| 64ビットのPowerShellで実行する（`run_as_32_bit`） | 画面のデフォルトは32ビット。64ビットのWindowsで32ビットのPowerShellを使うと、`HKLM:\SOFTWARE`への書き込みが`WOW6432Node`に振り替えられる |
| 署名の確認を強制する（`enforce_signature_check`） | 画面のデフォルトは有効で、信頼された発行元の署名が必要になる。署名しないスクリプトでは無効にする |

最も重要なのは、一度実行に成功したスクリプトが再実行されない点です。
IMEは、実行に成功したスクリプトを、スクリプトやポリシーが変わるまで再実行しません。
変わったかどうかは、スクリプトのハッシュで判断しているようです。
今回の検証でも、スクリプトの内容を変えてアップロードし直すと、IMEのログに次のように記録され、スクリプトが再実行されました。

```text title="IntuneManagementExtension.log（抜粋）"
[PowerShell] Policy id <スクリプトのID> for user <ユーザーのID> has different hash, reset download count. …
```

ハッシュが変わるため、コメントを一文字直しただけでも、割り当て先のすべてのWindowsデバイスで再実行されると考えられます。
反対に、内容を変えない限り、Windowsデバイスの値が書き換えられても再実行されません。
再実行されても問題がないように、スクリプトは何度実行しても同じ結果になるように書いておく必要があります。

失敗した場合（終了コードが0以外など）は、続く3回の問い合わせで再実行されます。
3回とも失敗すると、スクリプトが変わるまで実行されません。
また、スクリプトは200 KB未満にする必要があり、30分でタイムアウトします。

### スクリプトでレジストリに書き込む方法の弱点

スクリプトでレジストリに書き込む方法には、Policy CSPと比べて次の弱点があります。

- 配布をやめても、書き込んだ値は残る（入れ墨になる）
- 前述のとおり再実行されないため、利用者が値を書き換えても元に戻らない

1つ目は、スクリプトの中で対策できます。
2つ目は、後述する修復スクリプトで補えます。

### スクリプトの設計

今回は、書き込むレジストリの値をTerraformから渡す、汎用的なスクリプトを作りました。
方針は次のとおりです。

- 書き込む値の一覧をJSONで受け取り、Terraformの`templatefile()`でスクリプトに埋め込む
- 書き込んだ値の一覧をレジストリに記録し、次に実行したときに一覧から消えた値を削除する（入れ墨への対策）
- 削除する代わりに、デフォルト値（`default`）に戻すこともできる
- 型とデータがすでに同じ値は書き換えない
- 検出（`detect`）と適用（`apply`）の2つのモードを持ち、修復スクリプトにも使えるようにする

書き込む値は、次の形式で指定します。

```hcl
{
  path    = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode" # HKLM:\ か HKCU:\ で始まるキー
  name    = "UpdateMode"                                   # 値の名前
  type    = "String"                                       # String、ExpandString、MultiString、DWord、QWord
  value   = "manual"                                       # 書き込むデータ
  default = "default"                                      # 一覧から外したときに戻す値（省略すると値を削除）
}
```

スクリプトの全文は次のとおりです。
`${name}`、`${mode}`、`${settings_base64}`が、`templatefile()`で埋め込まれる変数です。

```powershell title="registry.ps1.tftpl"
# Applies registry values given by Terraform. Rendered with templatefile():
#   name             Identifier of this set of values, used to record what was written
#   mode             "apply" (platform script, remediation script) or "detect" (detection script)
#   settings_base64  base64encode(jsonencode(list of settings))
#
# A setting: { "path": "HKLM:\\SOFTWARE\\...", "name": "...", "type": "DWord", "value": 0, "default": 1 }
#   type     String, ExpandString, MultiString, DWord or QWord
#   default  Optional. Value to restore when the setting is removed from the list.
#            Without it, the value is deleted.

$ErrorActionPreference = 'Stop'

$Name = '${name}'
$Mode = '${mode}'
$SettingsBase64 = '${settings_base64}'

# Values this script wrote are recorded here, so that removed settings can be cleaned up.
# A script that runs as the signed-in user cannot write HKLM, so it records under HKCU.
if ([Security.Principal.WindowsIdentity]::GetCurrent().IsSystem) {
    $StateRoot = 'HKLM:\SOFTWARE\IntuneRegistrySettings'
} else {
    $StateRoot = 'HKCU:\SOFTWARE\IntuneRegistrySettings'
}

function Write-Log([string]$Message) {
    Write-Output "[$Name] $Message"
}

function Get-RegistryValueType([string]$Type) {
    $types = @{
        'String'       = [Microsoft.Win32.RegistryValueKind]::String
        'ExpandString' = [Microsoft.Win32.RegistryValueKind]::ExpandString
        'MultiString'  = [Microsoft.Win32.RegistryValueKind]::MultiString
        'DWord'        = [Microsoft.Win32.RegistryValueKind]::DWord
        'QWord'        = [Microsoft.Win32.RegistryValueKind]::QWord
    }
    if (-not $types.ContainsKey($Type)) {
        throw "Unsupported type '$Type'. Use String, ExpandString, MultiString, DWord or QWord."
    }
    return $types[$Type]
}

function ConvertTo-RegistryData($Value, [Microsoft.Win32.RegistryValueKind]$Kind) {
    switch ($Kind) {
        # Registry DWORD values are unsigned, but PowerShell writes them as Int32.
        'DWord'       { return [BitConverter]::ToInt32([BitConverter]::GetBytes([uint32][int64]$Value), 0) }
        'QWord'       { return [int64]$Value }
        'MultiString' { return [string[]]@($Value) }
        default       { return [string]$Value }
    }
}

# Returns $true when the value exists with the same type and data.
function Test-RegistryValue([string]$Path, [string]$ValueName, [Microsoft.Win32.RegistryValueKind]$Kind, $Data) {
    $key = Get-Item -LiteralPath $Path -ErrorAction SilentlyContinue
    if ($null -eq $key -or $key.GetValueNames() -notcontains $ValueName) {
        return $false
    }
    if ($key.GetValueKind($ValueName) -ne $Kind) {
        return $false
    }
    $current = $key.GetValue($ValueName, $null, 'DoNotExpandEnvironmentNames')
    if ($Kind -eq 'MultiString') {
        return (@($current) -join "`n") -ceq (@($Data) -join "`n")
    }
    return "$current" -ceq "$Data"
}

function Set-RegistryValue([string]$Path, [string]$ValueName, [Microsoft.Win32.RegistryValueKind]$Kind, $Data) {
    if (-not (Test-Path -LiteralPath $Path)) {
        New-Item -Path $Path -Force | Out-Null
    }
    New-ItemProperty -LiteralPath $Path -Name $ValueName -PropertyType $Kind -Value $Data -Force | Out-Null
}

# Windows PowerShell 5.1 returns a JSON array from ConvertFrom-Json as a single object.
# Passing it through the pipeline enumerates the elements.
function ConvertFrom-JsonArray([string]$Json) {
    return @(ConvertFrom-Json -InputObject $Json | ForEach-Object { $_ })
}

function Get-SettingKey($Setting) {
    return '{0}\{1}' -f $Setting.path, $Setting.name
}

try {
    if (@('apply', 'detect') -notcontains $Mode) {
        throw "Unsupported mode '$Mode'. Use apply or detect."
    }

    # A 32-bit process on 64-bit Windows writes HKLM:\SOFTWARE to WOW6432Node instead.
    if ([Environment]::Is64BitOperatingSystem -and -not [Environment]::Is64BitProcess) {
        throw 'Running as a 32-bit process. Set run_as_32_bit = false.'
    }

    $json = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($SettingsBase64))
    $settings = ConvertFrom-JsonArray $json

    $desired = [ordered]@{}
    foreach ($setting in $settings) {
        if ($setting.path -notmatch '^(HKLM|HKCU):\\') {
            throw "Path must start with HKLM:\ or HKCU:\ : '$($setting.path)'"
        }
        $kind = Get-RegistryValueType $setting.type
        $desired[(Get-SettingKey $setting)] = [pscustomobject]@{
            Setting = $setting
            Kind    = $kind
            Data    = ConvertTo-RegistryData $setting.value $kind
        }
    }

    # Settings written by the previous run.
    $statePath = Join-Path $StateRoot $Name
    $previous = @()
    $stateKey = Get-Item -LiteralPath $statePath -ErrorAction SilentlyContinue
    if ($null -ne $stateKey -and $stateKey.GetValueNames() -contains 'Settings') {
        $previous = ConvertFrom-JsonArray $stateKey.GetValue('Settings')
    }
    $removed = @($previous | Where-Object { -not $desired.Contains((Get-SettingKey $_)) })

    if ($Mode -eq 'detect') {
        $drift = @()
        foreach ($entry in $desired.Values) {
            if (-not (Test-RegistryValue $entry.Setting.path $entry.Setting.name $entry.Kind $entry.Data)) {
                $drift += Get-SettingKey $entry.Setting
            }
        }
        foreach ($setting in $removed) {
            $drift += '{0} (removed)' -f (Get-SettingKey $setting)
        }
        if ($drift.Count -gt 0) {
            Write-Log ('Not compliant: {0}' -f ($drift -join ', '))
            exit 1
        }
        Write-Log 'Compliant'
        exit 0
    }

    foreach ($entry in $desired.Values) {
        $key = Get-SettingKey $entry.Setting
        if (Test-RegistryValue $entry.Setting.path $entry.Setting.name $entry.Kind $entry.Data) {
            Write-Log "Unchanged: $key"
            continue
        }
        Set-RegistryValue $entry.Setting.path $entry.Setting.name $entry.Kind $entry.Data
        Write-Log "Set: $key"
    }

    foreach ($setting in $removed) {
        $key = Get-SettingKey $setting
        if ($null -ne $setting.default) {
            $kind = Get-RegistryValueType $setting.type
            Set-RegistryValue $setting.path $setting.name $kind (ConvertTo-RegistryData $setting.default $kind)
            Write-Log "Restored default: $key"
        } elseif ($null -ne (Get-ItemProperty -LiteralPath $setting.path -Name $setting.name -ErrorAction SilentlyContinue)) {
            Remove-ItemProperty -LiteralPath $setting.path -Name $setting.name
            Write-Log "Removed: $key"
        }
    }

    # Record what this run manages, for the next run.
    if (-not (Test-Path -LiteralPath $statePath)) {
        New-Item -Path $statePath -Force | Out-Null
    }
    $state = ConvertTo-Json -InputObject @($desired.Values | ForEach-Object { $_.Setting }) -Compress -Depth 5
    New-ItemProperty -LiteralPath $statePath -Name 'Settings' -PropertyType String -Value $state -Force | Out-Null

    Write-Log ('Applied {0} setting(s), cleaned up {1} removed setting(s)' -f $desired.Count, $removed.Count)
    exit 0
} catch {
    Write-Log "Failed: $($_.Exception.Message)"
    exit 1
}
```

いくつか補足します。

- JSONは`base64encode()`で埋め込んでいます。値に`'`が含まれていても、PowerShellの文字列が壊れないようにするためです
- 書き込んだ値の一覧は、SYSTEMで実行した場合は`HKLM:\SOFTWARE\IntuneRegistrySettings\<name>`に記録します
- 64ビットのWindowsで32ビットのPowerShellとして実行されると、`HKLM:\SOFTWARE`への書き込みが`WOW6432Node`に振り替えられます。そのため、32ビットで実行されたらエラーにしています
- Windows PowerShell 5.1の`ConvertFrom-Json`は、JSONの配列を1つのオブジェクトとして返します。そのまま`foreach`に渡すと要素に分かれないので、パイプラインを通して展開しています
- スクリプトのコメントとログは英語にしています。文字コードの違いで、Windows PowerShell 5.1が日本語を正しく読めない場合があるためです

このスクリプトは、Windows PowerShell 5.1で、値の追加、変更、削除、デフォルト値への復元、検出のそれぞれを確かめています。

### Terraformでプラットフォームスクリプトを配布する

プラットフォームスクリプトは、`windows_platform_script`で書きます。
VS Codeの自動更新を手動にし、テレメトリーを無効にする例です。

```hcl title="registry.tf"
locals {
  vscode_registry_settings = [
    {
      path  = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name  = "UpdateMode"
      type  = "String"
      value = "manual"
    },
    {
      path  = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name  = "TelemetryLevel"
      type  = "String"
      value = "off"
    },
  ]
}

resource "microsoft365_graph_beta_device_management_windows_platform_script" "vscode_registry" {
  display_name = "vscode-registry"
  file_name    = "vscode-registry.ps1"
  script_content = templatefile("${path.module}/registry.ps1.tftpl", {
    name            = "vscode"
    mode            = "apply"
    settings_base64 = base64encode(jsonencode(local.vscode_registry_settings))
  })
  run_as_account          = "system"
  run_as_32_bit           = false
  enforce_signature_check = false

  assignments = [
    {
      type = "allLicensedUsersAssignmentTarget"
    }
  ]
}
```

`HKLM`に書き込めるように、`run_as_account`は`system`にします。
`run_as_32_bit`は`false`にして、64ビットのPowerShellで実行します。

### Windowsデバイスでの動き

`apply`してから約10分後、IMEがスクリプトを受け取り、SYSTEMとして実行しました。
IMEのログ（`C:\ProgramData\Microsoft\IntuneManagementExtension\Logs\AgentExecutor.log`）には、スクリプトの出力が記録されています。

```text title="AgentExecutor.log（抜粋）"
[vscode] Set: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\UpdateMode
[vscode] Set: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\TelemetryLevel
[vscode] Applied 2 setting(s), cleaned up 0 removed setting(s)
```

`HKLM\SOFTWARE\Policies\Microsoft\VSCode`に、`UpdateMode`（`manual`）と`TelemetryLevel`（`off`）が書き込まれました。

次に、Terraformで`TelemetryLevel`を一覧から外し、`UpdateMode`を`none`に変えて`apply`しました。
`UpdateMode`には、一覧から外したときに戻すデフォルト値として`default`を指定しています。

```hcl title="registry.tf" ins={7-8} del={10-15}
locals {
  vscode_registry_settings = [
    {
      path    = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name    = "UpdateMode"
      type    = "String"
      value   = "none"
      default = "default"
    },
    {
      path  = "HKLM:\\SOFTWARE\\Policies\\Microsoft\\VSCode"
      name  = "TelemetryLevel"
      type  = "String"
      value = "off"
    },
  ]
}
```

Windowsデバイスを再起動すると、前述のとおり、IMEはスクリプトのハッシュが変わったことを検出し、スクリプトを再実行しました。

```text title="AgentExecutor.log（抜粋）"
[vscode] Set: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\UpdateMode
[vscode] Removed: HKLM:\SOFTWARE\Policies\Microsoft\VSCode\TelemetryLevel
[vscode] Applied 1 setting(s), cleaned up 1 removed setting(s)
```

`UpdateMode`は`none`に変わり、一覧から外した`TelemetryLevel`は削除されました。
値の一覧を変えると、`templatefile()`で埋め込んだスクリプトの内容が変わるため、IMEが再実行します。

今回は、`apply`から約5分後に、Windowsデバイスを再起動して同期したところで再実行されました。

また、プラットフォームスクリプトの割り当てを外したり削除したりしても、IMEは値を戻す処理を実行しません。
そのため、書き込んだ値は残ると考えられます（今回は確認していません）。
値を消したいときは、スクリプトを削除する前に一覧から外して`apply`し、Windowsデバイスで削除されたことを確認します。

## 修復スクリプトで値を保つ

プラットフォームスクリプトは、利用者や別のソフトウェアがレジストリの値を書き換えても元に戻しません。
定期的に値を確かめて戻したい場合は、修復スクリプト（Remediations）を使います。

修復スクリプトは、検出スクリプトと修復スクリプトの組で、指定した間隔で検出スクリプトを実行します。
検出スクリプトが`exit 1`で終わったときだけ、修復スクリプトが実行されます。
修復スクリプトを使うには、利用者にWindows Enterprise E3、E5などのライセンスが必要です。

前述のスクリプトは、`mode`を`detect`にすると、値が一覧と違う場合に`exit 1`で終わります。
同じテンプレートから、検出スクリプトと修復スクリプトの2つを作れます。

```hcl title="remediation.tf"
locals {
  vscode_registry_script = {
    name            = "vscode"
    settings_base64 = base64encode(jsonencode(local.vscode_registry_settings))
  }
}

resource "microsoft365_graph_beta_device_management_windows_remediation_script" "vscode_registry" {
  display_name   = "vscode-registry"
  publisher      = "IT"
  run_as_account = "system"
  run_as_32_bit  = false

  detection_script_content   = templatefile("${path.module}/registry.ps1.tftpl", merge(local.vscode_registry_script, { mode = "detect" }))
  remediation_script_content = templatefile("${path.module}/registry.ps1.tftpl", merge(local.vscode_registry_script, { mode = "apply" }))

  assignments = [
    {
      type = "allLicensedUsersAssignmentTarget"
      daily_schedule = {
        interval = 1
        time     = "09:00:00"
        use_utc  = false
      }
    },
  ]
}
```

筆者の環境にはライセンスがないため、修復スクリプトは`terraform validate`での確認までにとどめています。
検出と修復の動きは、Windows PowerShell 5.1でスクリプトを直接実行して確かめました。

## 終わりに

今回は、IntuneでADMXを運用するときの注意点を紹介しました。

ADMXのバージョンの更新では、新旧のポリシーが同じレジストリの値を書き込む状態を作らないことが大切です。
OMA-URIなら、AppNameとFileUidを固定して中身だけを差し替えると、安全に更新できました。
Policy CSPで書き込んだ値は、プロファイルを外すと削除され、入れ墨は起きませんでした。

ADMXで書き込めない場所は、スクリプトで書き込めます。
ただし、値の削除や、書き換えられた値を戻す処理は、自分で用意する必要があります。
Terraformで値の一覧とスクリプトをまとめて管理すると、こうした処理を1つのスクリプトに閉じ込められると思います。
